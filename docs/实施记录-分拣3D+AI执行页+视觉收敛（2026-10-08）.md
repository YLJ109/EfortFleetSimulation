## 2. AI 执行页（方案-点位推导与AI执行页）

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/ai/config` | 大模型开没开（**不回传 key**）、批量上限、是否真实下发 |
| POST | `/api/ai/parse` | **只解析不执行**；返回 `plan_id` + `echo`（人话回显）+ 批量件数 |
| POST | `/api/ai/exec` | 必须带**同一个** `plan_id`；批量/看颜色必须 `confirm` |
| GET | `/api/ai/state` | 进度（阶段/取料/判色/落料/停止原因）+ 本页占位表 |
| POST | `/api/ai/cancel` | 软停（步边界生效，随后回起点） |
| POST | `/api/ai/occ/reset` | 清空本页占位表 |

### 安全口径（逐条对照方案 §6 的问题清单）

| 方案里的问题 | 落地做法 |
|---|---|
| 大模型会"编" | `services/llm.py::sanitize()` 三道白名单：动作 ∈ 5 种、流程 op ∈ 4 种、格号必须 `^[AB][1-9]$`；编造 → **直接拒绝**并说明 |
| **不碰控制通道** | 大模型只输出受限 JSON；执行复用 `api/sorting.py` 的 `_move/_air/_capture`（**同一套**"写目标+触发位"实现） |
| 不是权限后门 | 6 个接口全挂 `require_control`（`test_ai.py` 逐个断言）；围栏/轴锁/速度/运行中互锁一个不少 |
| 语音误识 | 界面同时显示**识别原话**与可编辑输入；`plan_id` 绑定保证"确认的就是解析的那份" |
| 批量风险 | 上限默认 3（`EFORT_AI_BATCH_MAX`）；超过只跑前 N 件并在计划里写明；放到同一个具体格 → **拒绝**（会叠件） |
| 谁在动 | 运行中再来指令 → 409；分拣在跑时同样拒绝 |
| 审计 | 每条指令把**原话 + 计划 JSON + 结果**写事件表 |
| 无 key 可用 | 规则解析**永远先跑**；无 key 时页面显示"未配置（规则解析）"，不报错 |
| 延迟 | 单件、明确坐标可免确认（默认仍需确认；空跑默认开） |
| 相机只对 C 区 | "看颜色"按方案 (a) 实现：**去取来看**（是运动，必须确认），判完放回原格 |

### 已如实说明的局限（不是 bug，是当前能力边界）

- 本页「占位表」**不共享**分拣页那一轮运行的占位表，也**不知道 A/B 区真实里面有什么**
  （相机只对 C 区）。默认 A 区视为满、B 区为空，每成功搬一件才更新；页面已写清。
- 批量搬运的"随机"= **取件顺序随机**（按方案 §6 问题 3 的口径），不是随机放位。

## 3. 视觉口径收敛（方案-三色识别口径收敛 §3）

| 要求 | 落地 |
|---|---|
| 只识别矩形 | `vision_color.DEFAULT_THR` 新增 **`fill_min = 0.72`** 硬门槛：低于它直接判"非矩形(x.xx < y.yy)"、**不输出颜色**；填 0 = 关闭 |
| 太小的不要检测 | 已有 `min_side` / `min_area_ratio` / `min_area_abs` → 现在**上了面板**（3 个滑杆） |
| 置信度太低不要 | 已有 `conf_thr`（面板原有滑杆） |
| 为什么没检测到 | 服务端新增 `vision.last_miss`（未发现候选 / 非矩形 / 太小 / 低置信 / 非红绿蓝三色…）；面板显示"最近未检出：<原因>"；分拣判不出时把**逐帧真原因**写进停止文案 |

### 两个必须先核实的点（都核过了）

1. **`fill` 与旋转无关**：它 = 轮廓面积 ÷ **minAreaRect 长×宽**，不是轴对齐外接矩形。
   所以 0.72 的门槛**不会**误杀"斜着举的方块"（已用 0/12/30/45/78° 断言钉死）。
   —— 若按"轴对齐 bbox"算，45° 时 fill 会掉到 0.5，那才是真陷阱。
2. **诚实结论：这个硬门槛的实际行为变化比方案预期的小**。候选阶段本来就有
   `min_fill=0.45` + `solidity_min=0.75` 两道门，"能过候选却卡在 0.72"的形状很少
   （三角形、细长条在候选阶段就被挡了）。它真正的作用是把 **0.45~0.72 这个区间**
   从"只降置信度、标杂色（建议复核）"改成"明确判非矩形并给出原因"。
   现场真正好用的抓手是 `min_side` / `min_area_ratio` / `conf_thr` —— 这三个都在面板上。

## 9. 第三轮现场反馈（同日 · 三件事）

用户原话：**"1. 19 个摆放的 3D 物体怎么悬浮起来了啊，放在地上啊，合理的去做啊
2. 吸气一直吸住吧，到了 B 区停止吸气然后再放气 0.5 秒，停止放气改下逻辑吧"**，

### 9.1 悬浮的**根因**（我上一轮判断错了，先记在这里）

**把示教点的 Z 当成了"料的高度"。** 示教点存的是关节角，FK 算出来的是**法兰中心**
（工具安装面），**不是料的表面** —— 料在工具下方，低着"一个末端工具长度"。

证据（`/api/sorting/blocks` + 直接查库 FK）：

| 证据 | 数值 | 说明 |
|---|---|---|
| `A1` 法兰 Z / `A1上` Z | 145.94 / 180.28 mm | **只差 34.3mm 且是纯竖直** = 抬升避让 ⇒ 料厚 ≤34mm |
| 上一轮把 `plane_z=149.9` 当料高 | 料被画到台面上方 **150mm** | 看着就是悬空 15cm |
| A/B/C 实测 X/Y | X 285~578、Y ±446 mm | **全在站台台面范围内（±655mm）** ⇒ 就是坐在台面上 |

**修法**：新增 `plane_h_mm`（默认 0 = 站台台面 = 机器人底座平面），托盘/料/相机
底面统一坐这个面；`plane_z` 降级为**体检数据**（示教共面性），不再参与摆放。
物理细节：**托盘底面坐台面、料底面坐托盘内底面**（高一个托盘板厚 4mm）。

实测结果（`npm run preview:3d` + `plane_h=0`）：

```
落地检查：21 个物体的底面最大偏差 0.000 mm ✓ 全部落到实处（不悬浮）
托盘盒A 293.0×269.1mm / 托盘盒B 291.5×265.7mm，两盒间隙 44.5mm ✓ 不重叠
相机底座 (478.81, −7.44, 0) mm —— 镜头朝上，坐在台面上
```

### 9.2 吸气时序（顺序即工艺）

| | 旧 | 新（用户口径） |
|---|---|---|
| 取料后 | 抬起 → **停止吸**（负压阀断掉，靠残余真空吊件飞一路） | **一直吸住** |
| 送检 | 阀已断 | 阀保持开 |
| 到 B 正上方 | 放气 → 等 `blow_ms` → **回起点后才**停止放气 | **停止吸 → 放气 → 等 500ms → 就地停止放气** → 回起点 |

- `blow_ms` 语义随之变为**放气持续时间**，默认 **0 → 500ms**（前端标签 `放气后停留` → `放气时长`）。
- ★ **新增安全收口**：吸气现在会保持到 B 区，万一中途停（检测不到 / 列满 / 人工停止 /
  内部异常），阀会一直开着 —— 这是真隐患。现在**三条退出路径**（`_Stop`、内部异常、
  `finally` 兜底）都会 best-effort 关掉两路气，且异常时**只关阀不吹气**（半空吹会把件吹飞）。

### 9.3 J6 末端工具三改（`three/endEffector.js`）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| ③ | 工具没连在 J6 上、有缝 | 最靠后的零件在 `z=EE_FACE(8)`，与法兰面之间**空着 8 设计单位 = 16mm** | `EE_BACK = −2`（≈−3mm，轻微压进法兰面）：定位盘跨 −2..8、立板跨 −2..88，**都跨过法兰面**，且立板与定位盘实体相交 |
| ① | 工具偏大 | `EE_SCALE = 2` → 长 196 / 宽 218 / 立板 100mm | `EE_SCALE = 1.5` → **长 135 / 宽 163.5 / 高 90mm** |
| ② | 吸盘要向前 | 吸盘摆在立板**正中** `plateZ` | 前移到 `plateZ + CUP_FWD(15)` → 吸盘 z **87mm**（立板中心 64.5mm） |

新工具 `EE_META = { back:−2, scale:1.5, cupFwd:15, flangeT:10 }`（已外露供回归断言）。

用户原话：**"怎么绿色无法检测呀？全面检测代码，红蓝绿必须要检测"**。

### 10.1 现场证据（不是我猜的 —— 服务自报 + 真机日志）

### 10.2 用 **6524 张现场图**逐张量出的四个问题

新增 `camera/tools/vision_replay_test.py`（真图回放）后，逐张量出中间量：

| 图 | 标的 | HSV 色相（真值） | fill | 实测 Lab | ΔE vs 色卡 | 旧代码结果 |
|---|---|---|---|---|---|---|
| 155729 红 | 红 | H=4，R 199397 ✓ | 0.98 | L15 a12 b8 | **34.2** | 红，但 **conf=0.00** → 被过滤 |
| 154202 绿 | 绿 | H=70 ✓ | **0.71** | L54 a-26 b12 | 14.1 | **非矩形(0.71<0.72)** → 不给颜色 |
| 210746 蓝 | 蓝 | H=106 ✓ | **0.67** | L17 a-1 b-13 | 21.6 | **非矩形(0.67<0.72)** → 不给颜色 |

**关键结论：HSV 色相投票 100% 正确，颜色从来没判错；错的是后面两道门。**
而且**问题不止绿色** —— 红/蓝同样中招（用户只看到了绿色那个最明显的）。

### 10.3 四处修复

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| **1** | `fill_min=0.72` 误杀 | 只按**合成图**定的（合成图 fill≈0.95+），而现场真矩形 fill 只有 **0.67~0.75**（透视斜视+边缘模糊）→ 0.72 正好卡在分布正中 | 默认 **0.72 → 0.55**（低于实测最低 0.67 达 0.12 余量）；并把"软提示线"拆成独立项 `fill_warn`，不再与硬门槛共用一个数 |
| **2** | `conf = min(hsv_conf, lab_conf)` **一票否决** | Lab 用**固定标准色卡**（红 a*=69.2）比色，现场光照下实测 a*=12~14 → ΔE 26~34 → `lab_conf = 1-ΔE/25 = 0` → **形状完美（fill=0.98）的红块 conf=0.00** | **改以 HSV 一致性为主判据**：Lab 一致→conf×1.15（封顶 1.0）；分歧→×0.55（降但不归零）；ΔE>20 只写进 reason 提示"建议现场标定" |
| **3** | `dominant_lab` **直接崩** | `np.random.choice(size=n, replace=False, p=w)` 有一条硬约束：**p 的非零个数必须 ≥ n**；中心加权 `exp(-d²/2σ²)` 在远处下溢成 0 → `ValueError: Fewer non-zero entries in p than size` → 整帧 `detect()` 抛异常 | 只在**非零权重池**里采样；池不足时退回"允许重复"（加权有放回）。大色块 + 全画幅掩膜实测均不再崩，连续 12 张 0 异常 |
| **4** | 绿带与蓝带之间有 **5° 空隙** | 绿 [35,90)、蓝 [95,135) → 偏青的绿（H=91~94）**两条带都不占** → 判不出 | 绿带接到 **95**（与蓝带起点无缝）；副作用（如实写明）：偏青物体现在归"绿"，比"都不认"更可用 |

### 10.4 顺带：让"检测不到"能指导现场行动

新增 `vision_color.explain_no_candidate()`，按**与 `find_rectangles` 相同的门槛顺序**给出具体原因。
接进 `camera_service._miss_reason()`（现场面板原样显示）：

```
物体超出画面（贴上/下边缘，被裁掉）：把方块完整放进画面再测（当前彩色块 197086 px，短边 538 px）
彩色块太小：1200 px（需要 ≥ 2500 px）：把方块放近些或调大焦距
形状不完整（实心度 0.66 < 0.75）：可能被遮挡 / 有缺口 / 只露出一部分
```

★ 以前一律报"未发现候选（可能太小/太暗/颜色不在红绿蓝）"—— 而实测最常见的真因是
**"物体怼到镜头前、超出画面"**，那句话完全指不到它，现场只能瞎试。

### 10.8 判色阈值的使用纪律（写进代码注释了，这里再强调一次）
