# 方案 · 三色方块分拣页（独立页 · 38 点位 · 经控制器 210 执行）

> 2026-10-08 · 现场需求（用户口述）：
> 独立分拣页；我给 37 个点位你照这个执行；机器人拿方块到摄像头**停顿 1 秒**，
> 摄像头**捕捉几帧**，按颜色放放料区；**吸不到 / 空跑 / 检测不到 → 直接停止**；
> **对满了停**；另给**一个**「开始/结束点」（开始与结束是**同一个点**）。
> ★ 2026-10-08 修正：**开始点与结束点是同一个点位** → 合计 **38** 个（37 + 1），不是 39。
> ★ 2026-10-08 追加（用户确认）：
>   ① 现场**四路气路（吸/停止吸/放/停止放）已实测全部可用**；
>   ② **不做真空压力检测** —— 做不到就直接停；
>   ③ **异常停止后要「回到起点」**（回到开始/结束点），不是原地撂着。
> 方案见 docs/规范-RPL程序编写规范与200服务程序.md（点位/执行口径）

## 1. 范围

| | 内容 |
|---|---|
| **做** | 独立「分拣」页；38 个点位体检与映射；一键开始分拣；每件：取料 → 送检（停顿+抓帧判色）→ 按色放料；异常即停；进度与实时判色可看；暂停/继续/停止 |
| **不做** | **不做任何自动恢复/重试绕行**（用户明确要求异常直接停）；不做视觉定位（槽位靠示教点位，不做像素→机器人坐标换算）；不做多路并行；不接语音指令 |

★ **安全红线**：分拣是**运动流程**，全部走既有安全链路（围栏互锁 / 轴锁 / 急停 / 报警守卫 / 统一速度）。
语音字幕等只读功能**不得**介入控制（已有 `test_asr` 用例钉死）。

## 2. 点位：38 个（37 + 开始/结束共用 1 个）

| 组 | 名称 | 数量 | 用途 |
|---|---|---|---|
| A 区 | `A1`…`A9` | 9 | 原料槽位（取料下落点） |
| A 区 | `A1上`…`A9上` | 9 | 对应槽位的**正上方**（安全高度/抬升落点） |
| B 区 | `B1`…`B9` | 9 | 放料槽位（放料下落点） |
| B 区 | `B1上`…`B9上` | 9 | 对应槽位的**正上方** |
| C 区 | `C检测` | 1 | 摄像头检测位（举件停留处） |
| 分拣 | `开始/结束点` | 1 | 一轮开始前先去、9 件跑完后**回到同一个点** |
| | | **38** | |

**B 区列序**：`B1/B4/B7` = 第 1 列（红）、`B2/B5/B8` = 第 2 列（绿）、`B3/B6/B9` = 第 3 列（蓝）。
（若现场实际行列与此不一致，改 `config/sorting.json` 的映射即可，不改代码。）

**存储方式**：建议 38 个点统一放进 `Point.group = "分拣"`（页面一次查全），
名字按上表命名 → 页面**默认按名字自动匹配**；同时提供**映射表**可手工改绑
（存 `config/sorting.json`），避免以后改名就把功能弄哑。**缺任何一个点，页面拒绝启动并列出缺哪些。**

## 3. 单件流程（共 9 件）

```
开始/结束点 →（对 i = A1…A9）
  ① 移到 A{i}上 → 移到 A{i}（下落）
  ② 吸（40135.Bit1，等完成位）
  ③ 抬起 → 移到 C检测 → 停顿 1.0s（可配）→ 抓 N 帧判色（默认 3 帧）
  ④ 按颜色选 B 目标：红→列1 / 绿→列2 / 蓝→列3，取该列**下一个未占用的行**
  ⑤ 移到 B{j}上 → 移到 B{j}（下落）
  ⑥ 停止吸（40135.Bit2）→ 抬起
  ⑦ 回 A 区取下一件
→ 9 件完成后 → 回到开始/结束点（同一个点）
```

**为什么要"抬起"再移动**：A/B 槽位是下落点，直接横移会撞工装 —— 所以每槽都示教了"正上方"。

## 4. 判色策略（C 区）

- **抓帧**：停留 1s 后，**连续调 N 次** 视觉服务的 `GET /vision/detect`（同步返回一次判定），
  间隔 ~150ms（可配）。为什么用 `/vision/detect` 而不是 `/vision/last`：
  前者**主动、同步、时机可控**；后者是自动线程的游标事件流，适合界面订阅，不适合"我现在就要一帧结论"。
- **采信规则**：N 帧里取**多数一致**的颜色（如 3 帧里 2 帧红 → 红）。
  要求命中帧数 ≥ `ceil(N/2)`，且 `conf ≥ 现场阈值`（复用 `/vision/status` 的 `min_conf`）。
- **判定为"检测不到"**（→ 停止）：① 帧间结论不一致；② 全部 `未知`；③ `conf` 低于阈值；④ 相机未开/服务不可达。
- **前置条件**：视觉服务在跑、相机已开且 `color_capable=true`、颜色识别开启（颜色线程 `thread_alive`）。
  不满足时页面**拒绝启动**并说明差哪一项（不给"跑了但永远判不出色"的假象）。

## 5. ★ 一个必须如实说明的限制：**"吸不到"目前检测不了**

用户要求"吸不到就停"，但**控制器没有真空压力反馈**：210 的吸气完成位只表示
"触发位被响应、`io.DOut[N]` 已写"，**不代表方块真的被吸住**。因此可选判据只有：

| 判据 | 能发现什么 | 现状 |
|---|---|---|
| A. 吸气完成位未置位 | 通信/程序层失败（如 210 没跑、触发被拒） | **采用** |
| B. **到 C 区抓帧时画面上没有目标 / 判不出颜色** | 夹爪上没东西（吸不到、空跑、中途掉了） | **采用（主判据）** |
| C. 真空压力开关/负压传感器 | 真正的"吸住没吸住" | **现场没有 → 不做**（用户 2026-10-08 确认） |

**结论（定稿）**：不引入任何真空反馈硬件。
把"吸不到 / 空跑 / 检测不到"合并为同一判据 —— **到 C 区拍不到方块或判不出颜色 → 停止**。
代价：要跑到 C 区才发现，白跑一段；换来实现简单、无额外硬件依赖。

## 5.5 异常处理：**停止 → 回到开始/结束点**（用户 2026-10-08 追加）

任何异常（吸不到 / 空跑 / 检测不到 / 该列已满 / 通信或视觉服务失败）统一走同一条收尾：

```
异常判定 → 立即停止后续动作（不再下发新的运动/IO）
        → 移到「开始/结束点」       ← ★ 不是原地撂着，也不是回 A 槽
        → 结束本轮（界面显示失败原因 + 停在第几件）
```

- **夹爪状态**：默认**保持当前状态回原点**（吸着就带件回去，没吸到就空着回去）——
  理由：把不知颜色的件随便丢在 C 区/槽位上，可能砸到工装或滚进机构；
  带回原点由人来处理更稳。配置项 `error_keep_grip`（默认 true）可改成"先停止吸/放气再回原点"。
- **回原点也要受保护**：同样走围栏/轴锁/急停/速度；若回程中被"停止执行"打断，就停在当前位置（不再硬走）。
- **可选保留人工接管**：异常停止后如需手动把件放回 A 槽，操作员可用既有手动执行/点动功能，不在本流程内自动做。

## 6. "对满了停"

- 运行时维护一张**本轮占位表**（内存，不落库）：`列(红/绿/蓝) → 已放行号列表`。
- 每件判色后取该列"下一个未占用行"（1→3 依次）。
- 当某列 3 行已占满、而**又来一件同色** → **立即停止 → 回开始/结束点**，提示"红列已满（3/3）"。
- 9 件正常跑完（3/3/3）不算满，收尾回开始/结束点。
- 页面显示三列占用情况（●●● / ○○○），一眼看出进度。

## 7. 后端设计

- **新增 `services/sorting_runner.py`**：分拣流程引擎，单实例（同一时间只跑一路）。
- **复用既有执行器设施**（不另起一套并发）：
  - 注册进 `_RUN_ACTIVE`（与序列/文件执行共用互锁与"停止"语义）；
  - 进度与状态走既有 `GET /api/control/run-state`（扩展 `kind="sorting"` 与
    `piece`/`total`/`stage`/`color` 字段）；
  - 暂停/继续/停止复用 `/control/run-pause` `/run-resume` `/control/run-cancel`
    （点动/吸放等"步中"不可暂停，与既有语义一致）。
- **每步下发**：`motion.command(...)`（写目标 + 40135.Bit0 → 常驻 210 执行 MJOINT）；
  吸/停止吸走 `rc_vacuum`（Bit1/Bit2）。**不加载新程序**，不碰 210。
- **前置体检**（启动前一次性做完，任一不过就拒绝启动）：38 点位齐备且可解析、视觉服务可用、
  一体就绪（伺服/档位/报警/急停）、持有控制令牌、"真实下发"总闸开启。
- **接口**：
  | 方法 | 路径 | 说明 |
  |---|---|---|
  | `GET` | `/api/sorting/points` | 38 点位体检结果 + 当前映射（缺哪些、名字对不上哪些） |
  | `POST` | `/api/sorting/points` | 保存映射（可选，改名后重新对位） |
  | `GET` | `/api/sorting/config` | 停顿时长/抓帧数/置信度阈值/列映射/异常策略（只读回显） |
  | `POST` | `/api/sorting/start` | 开始分拣（可带 `dry_run=true` 空跑：只校验与判色，不下发运动） |
  | `GET` | `/api/sorting/state` | 进度快照（第几件、阶段、本次判色、三列占用、最近错误） |
  | `POST` | `/api/sorting/cancel` | 停止（等价 `/control/run-cancel`，语义一致） |

## 修订（2026-10-08 现场反馈后）

### R1. 判色只在"物体真的到 C 区"时才做（修"已停止：检测不到"）
现场报"已停止：检测不到（无有效判定（全部未知或置信度低于 0.28））"，但**物体根本没取、
没到摄像头前**。根因：判色在"机器人根本没动"的情况下也照做 —— 空跑会跳过全部运动，
双闸未开时运动只走仿真，两种情况相机前面都没有方块，必然判不出来 → 第一件就停。
修正：
- **空跑 / 双闸未开**：`judge = (not dry) and real_write_enabled()` 为假 → **不调相机、
  不判色、不因"检测不到"停**；用轮换占位色（红/绿/蓝）把"点位 + 选槽 + 落料"跑通，
  state 标 `judge:false` / `sim_color:true`，界面明说"空跑占位色（未判色）"。
- **真实下发**：判色前先校验**确实到达 C 检测点**（`CAM_ARRIVE_TOL_DEG = 3.0°`），
  没到就如实报"未到达 C 检测点（实际偏差 X°）"，不再含糊地说"检测不到"。
- 启动前置校验（视觉服务在线/彩色/线程活着）**只在真的要判色时要求** ——
  空跑不再被"相机没开"挡住。

### R2. 分拣页运行日志
分拣页此前无任何运行日志。现日志写进全局 `exec.log`，由 `MonitorLayout` 左下角浮动面板
统一显示（与程序执行/点位执行同一块，不另做一套）：视图白名单加入 `sort`；
按"阶段/件数/判色/落料槽/停止原因"的变化写行（轮询 800ms，逐帧记会刷屏）。
