# 方案 · 分拣 3D 可视化（18 个方块跟随执行同步）

> 2026-10-08 · 用户口径：
> A 区每个槽位放一个**黑色矩形**代表原料；机器人拿到摄像头，摄像头分完颜色 → 矩形**变成识别的颜色**；
> B 区放料区也放**九个槽位**；**每个点都标好了**（示教点位）；依据它做一个 3D 物体放在那；
> **根据代码同步执行**；先思考做方案，再去实现，然后**报存在的问题**。

---

## 1. 目标与范围

| | 内容 |
|---|---|
| **做** | 分拣页 3D 视口里可视化 18 个槽位：A 区 9 个方块、B 区 9 个槽位；方块随分拣流程消失/搬运/变色/落位；由 `/api/sorting/state` 驱动 |
| **不做** | 不做视觉定位（方块位置来自**示教点位**，不是相机识别的实际位置）；不做物理仿真（不模拟碰撞/掉落）；不做真机以外的状态推断 |

## 2. 物体设计

**★ 平面与不重叠（用户 2026-10-08 明确要求：全部在平面上、不能漂浮、不能重叠）**

- 18 个槽位 + C 检测点**都有示教坐标** → 方块位置来自它们；但**方块底面的高度取统一平面值**，
  不直接用各点示教的 Z（示教必有零点几毫米误差，直接用会出现"有的悬空、有的埋进去"）：
  `planeZ = median(各槽位示教点 Z)`，方块底面贴在 `planeZ` 上 →
  **所有方块同高、绝不漂浮**（同理 C 区摄像头按 `C检测` 的 Z + H 抬高）。
- **不重叠检查**：任两槽位中心距 < 方块边长 × 1.05 → 判"重叠风险"，
  页面**列出来并拒绝画那两个**（而不是默默叠在一起）。这是"保证不重叠"的落地方式。
- 方块尺寸待定（见 §9 第 1 条）；默认 30×30×12mm。

| 位置 | 初始 | 执行中 | 说明 |
|---|---|---|---|
| A 区 9 格 | **黑色实心扁方块**（代表有料） | 被取走 → **消失**；取料中的那格高亮 | 顺序 A1→A9 |
| 手上（跟随夹爪） | — | 取到后**挂在夹爪上**，到 C 区判色后**变成红/绿/蓝** | 用户要求"来到摄像头…矩形变成识别的颜色"，所以变色发生在**手上那块** |
| B 区 9 格 | **槽位底框**（虚线/半透明，表示空槽） | 放入后 → **实心彩色方块**（按列：1 红 2 绿 3 蓝） | ★ 见问题清单第 4 条：B 区初始应该是**空**的 |
| **C 检测工位** | **一个摄像头模型**（机身 + 镜头，镜头朝下） | 判色时**闪一下**（示意正在拍） | ★ 相机摆在示教点 `C检测` 的**正上方**、镜头朝下 —— 机器人把料举到它下面拍（见问题清单第 12 条）|

**尺寸/外观约定**（避免与残影混淆，见问题清单第 5 条）：
- 方块：30×30×12mm（按现场实物尺寸可配），实心、`flatShading`，黑=未分拣 / 红绿蓝=已识别
- B 区底框：同尺寸**线框**（`EdgesGeometry`），灰白
- 与残影（半透明蓝/橙）在**实心 vs 半透明**上天然区分；蓝色方块用**深蓝 + 描边**，不用残影那种亮蓝

## 3. 位置从哪来（★ 本方案最关键的一环）

**示教点存的是关节角，必须做 FK 才能变成 3D 位置。而前端没有可复用的 FK 模块**
（`tools/verify_kinematics.mjs` 是在 Node 里**内联复刻**了一份 DH 链用于对拍，不是可 import 的模块）。

→ **决定：由后端算，通过接口下发位置。**

```
GET /api/sorting/blocks
  → { ok, unit:"scene", slots: [
        {"name":"A1",    "role":"A",  "pos":[x,y,z], "taught":true},
        {"name":"A1上",  ...},
        {"name":"B1",    "role":"B",  ...}, ... ] }
```

- 后端用现成的 `forward_kinematics(joints)` / `fk_matrix` 求出各槽位**末端位置**；
- **坐标系对齐**：后端 FK 是「机器人基座系、mm」，3D 场景是「three.js Y-up、米、且机器人站在台面上（`baseLiftY()`）」。
  必须做一次映射并**实测校验**（见实施步骤 3），否则方块会飘在错误位置。
- 未示教的点 → `taught:false`，前端**不画**那一个（连同它的底框），并在体检卡提示。

## 4. 状态同步（"根据代码同步执行"）

数据源就是已有的 `/api/sorting/state`，**不新增状态机**：

| 3D 表现 | 来自 state 的字段 | 备注 |
|---|---|---|
| A 区哪几格已空 | `piece`（第 n 件 = 正在取 A n）| A1..A(n-1) 消失 |
| 手上有没有件 / 在哪个阶段 | `stage` + `piece` | `取料·吸` 之后 = 手上有件 |
| 手上件的颜色 | `color`（判色后才有） | 判色前显示"未知灰" |
| B 区哪格放了什么色 | `placement[]`（**已有**，含每列已用槽位）| 直接驱动 B 区方块 |
| 空跑/真实 | `dry_run` | 空跑时**整体标注"空跑：仅示意"**（机器人不动）|

**需要给 state 补 2 个字段**（现在没有，纯增量）：
- `holding`：手上是否有件（判断"取料吸合完成 → 到放料脱件"之间）
- `stage_zh` 或直接复用 `stage` 字符串做映射（避免前端硬编码中文字符串，易碎）

## 5. 实现路径（3D 侧）

- 新增 `src/three/sortingBlocks.js`：`createSortingBlocks()` →
  `{ root, setSlots(list), update(state), step(dt), dispose() }`
  - 用 `BoxGeometry` + `MeshLambertMaterial`（项目已有光照/环境贴图，**不用**新光源）
  - "手上那块"的做法：把它 `attach()` 到机器人的 **flangeNode**（`robotModel` 有 flangeNode），
    这样移动/姿态自动跟随，不需要每帧算位置；放料时再 `attach()` 回场景
  - `dispose()` 释放 geometry/material（项目对资源释放有硬要求）
- `src/three/manager.js`：与 `cell`/`lab` 同样方式创建、加进 `step()`、`dispose` 数组、复位置 null；
  导出 `setSortingSlots / updateSortingState / showSortingBlocks`
- 分拣页：挂载时拉 `/api/sorting/blocks` → `setSortingSlots`；轮询 state 时 `updateSortingState`

## 6. ★★ 存在的问题（要求如实报，逐条给影响与对策）

| # | 问题 | 影响 | 对策 / 需你确认 |
|---|---|---|---|
| **1** | **方块位置来自示教点位，不是相机识别的真实位置** | 别人可能误以为这是"视觉识别出的方块位置"；实际 A 区方块是**人工随机摆**的，3D 里只能摆在示教的那个槽位中心 | 界面**明确标注**「按示教点位示意，非视觉定位」；真要显示实际位置得做**像素→机器人坐标标定**（另一件事） |
| **2** | **坐标系对齐没实证** | 后端 FK 是机器人基座系(mm)，3D 是 Y-up(m)+台面抬升；映射错 → 方块整体偏移/悬空/埋进台面 | 必须先做一次**实测校验**：拿一个已示教槽位，比较 FK 位置与 3D 里机器人末端实际所在位置的球心差；差 >20mm 就先修映射再往下做 |
| **3** | **A 区"随机摆放"只体现在颜色，不体现在位置** | 3D 里 9 个黑块位置是固定的槽位中心；若现场某次方块没摆在格子里，3D 仍然显示在格子中心 → **虚报** | 同上第 1 条；或以后接视觉真实坐标（现在不做） |
| **4** | ~~B 区初始该不该有 9 个矩形？~~ | **已按"空槽底框"实现**；若要 9 个黑块请说（见 §9 第 2 条） | — |
| **9** | ~~A 区方块"消失"是逻辑推断~~ | **用户已答复**：吸不住 → 3D 也**不显示吸住**。落地方案：`stage` 到"取料·吸"之后才算吸住；一旦因**吸不到/空跑/检测不到**而停止 → **方块画回 A 格并标红**（不带走、不显示夹持）。同时界面注明这是**按流程推断**，不是真空传感器实测 | — |
| **5** | **蓝色方块与残影 A 撞色** | 残影 A 是淡蓝(#2f9bff)半透明，蓝方块若也用亮蓝 → 同屏分不清哪个是残影、哪个是料 | 蓝方块用**深蓝 #1F4FD8 + 描边**；残影保持半透明 —— 已按此实现 |
| **6** | **同步有最大 ~0.8s 延迟** | 3D 靠轮询 `/sorting/state`（800ms）驱动；真机上会看到"机器人已经动了、方块还慢半拍" | 可在分拣运行时把轮询降到 **200ms**（只在运行中提速，空闲恢复） |
| **7** | **空跑(dry_run) 时机器人不动，3D 却会"演"** | 容易被误当成真机在动 | 空跑时 3D 视口**打角标「空跑·仅示意」**，且方块只在 A/B 之间跳变、不做搬运动画 |
| **8** | **异常/停止时手上那块怎么显示** | 停止在半路（如在 C 区）时，方块该留在手上还是飞回 A？ | 建议：**留在手上**（如实反映"还夹着"），并在卡片上显示停止原因；不自动回位（回位就是编故事） |
| **9** | **A 区方块"消失"是逻辑推断，不是传感器** | 3D 里方块消失只代表"程序认为取走了"；真机吸不到时（现场无真空反馈）方块其实还在原地，但 3D 已经把它抹掉了 | ★ 这是**最会误导**的一条：建议**吸不到停止时把该方块画回 A 区**并标红，表示"疑似没取到"；但这同样只是推断 —— 需你确认要不要这么做 |
| **10** | **未示教的槽位画不出来** | 示教不完（不足 38 点）时，3D 是**残缺**的 | 已设计 `taught:false` → 不画 + 体检卡提示缺哪些，**不猜位置** |
| **11** | 性能 | 18 个盒子 + 少量材质，可忽略；但每帧 `attach/detach` 若写错会泄漏 group | 只在状态**变化**时 attach/detach，不在 `step()` 里做 |
| **12** | **相机模型摆哪、朝向怎么定？** | 示教点 `C检测` 是**机器人举料的位置**，真实相机装在它**上方**（往下拍）。但"上方多高、什么角度"只有现场知道，示教点里没有这个信息 | 默认按 `C检测` 点 **+Z 抬高 H、镜头朝下** 画（H 可配，默认 250mm），并明确标注这是示意；要精确就再加一个"相机安装点"示教（第 39 个点），或直接改 H |
| **13** | 相机模型会**挡住视线** | 它悬在 C 区上方，3D 里可能正好挡住机器人/方块 | 模型做小（约 60×60×80mm）+ 半透明外壳；必要时给一个"隐藏相机模型"开关 |

## 7. 实施步骤

1. 后端：`GET /api/sorting/blocks`（FK 求并返回 18 槽位场景坐标 + `taught`）；`/state` 补 `holding`
2. **坐标对齐实测校验**（问题 2）：拿已示教点对比 FK 与 3D 末端位置，确认映射系数（mm→m、Y-up、台面抬升）
3. 3D：`sortingBlocks.js`（18 槽位方块 + B 区底框 + C 区摄像头模型）+ manager 接线
4. 分拣页：挂载拉槽位、轮询驱动、空跑角标、缺项提示
5. 校验：`npm run verify` + 新增 headless 断言（方块数=已示教槽位数、颜色映射正确、dispose 干净）
6. 真机：示教几个点 → 看方块是否落在对应槽位 → 空跑看流程 → 真机单件看搬运/变色
