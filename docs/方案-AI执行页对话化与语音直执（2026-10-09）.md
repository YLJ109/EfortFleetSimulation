# 方案：AI 执行页 → 对话式语音控制台（2026-10-09）

> 需求原话（两条合并）：
> ① "指令输入做一个跟大冒险对话吧，下方也要提示那些可执行的文本提示，然后 ai 聊天过程中
>    逻辑没问题，通过语音确认直接说执行，ai 立刻执行不用等待用户点击按钮，如果触发过程当中
>    用户让它停，或者下达了别的指令，必须回到起点再开始执行用户的命令，保证丝滑完成任务"
> ② "点击空格说话，再点一次就停止对话"
>
> 交付要求：先思考 → 完善 → 制作方案 → **优化方案** → 再执行。

---

## 1. 需求拆解（5 条硬要求 + 1 条交互）

| # | 要求 | 关键难点 |
|---|---|---|
| R1 | 指令输入改成**对话式** | 现有是"表单 + 结果卡"，要变成消息流 |
| R2 | 下方提示**可执行文本** | 已有 7 条 preset，要补全并按能力分组 |
| R3 | 对话逻辑顺，**语音说"执行"就立刻执行**，不用点按钮 | 要区分"确认词"与"新指令"，且不能误触发 |
| R4 | 执行中**被打断（停/新指令）→ 先回起点 → 再执行新命令** | ★ 最难：需要"接管"机制，且不能变成急停 |
| R5 | 保证**丝滑** | 反馈要即时、进度要可见、不能卡 |
| R6 | **空格键**开关语音（按一次说，再按一次停） | 不能和输入框里的空格冲突 |

## 2. 现状与差距

| 现有能力 | 位置 | 差距 |
|---|---|---|
| 规则解析（5 类意图） | `nl_intent.py`：`look_color / move_one / move_all / sorting / estop` | 够用，不用改 |
| 解析→执行两步（`plan_id` 绑定 + 回显确认） | `api/ai.py` `/parse` `/exec` | **保留**（这是安全设计，不推翻）|
| 语音识别（腾讯云 ASR） | `stores/asr.js` + `services/asr_tencent.py` | 已有 `finalText` 定稿回调，可直接用 |
| 执行进度 / 取消 | `/ai/state` `/ai/cancel`；`_run` **异常一律回起点** | ★ **回起点已有**，缺的是"接管" |
| 执行中再来指令 | `/ai/exec` 直接 **409 拒绝** | ★ 正是要改的地方 |
| 交互形态 | `AiControlView.vue`：表单 + 解析结果卡 + 按钮 | 要改成对话流 |

**结论：底层能力齐了，这一轮主要是"交互重构 + 接管机制"。不改判色/运动链路。**

## 3. 设计

### 3.1 交互形态（对话流）

```
┌─ 对话区（自动滚到底） ───────────────────────────────────┐
│ 🤖  说吧，我在听 —— 也可以按 【空格】 直接说话            │
│ 👤  把A区第1行第1列放到B区红列                            │
│ 🤖  我理解为：                                        ⚠   │
│     ┌──────────────────────────────────────────┐        │
│     │ A1 → B区红列（第 1 个空位 B1）             │        │
│     │ [ 执行 ]  [ 取消 ]   或直接说「执行」       │        │
│     └──────────────────────────────────────────┘        │
│ 👤  执行                                                 │
│ 🤖  ▶ 开始执行（真实下发）                                │
│     · A1 上方 → 落到位 → 吸取 → 停 0.5s → 抬起            │
│     · 判色：红（conf 0.96）                              │
│     · 落料：B1                                           │
│ 🤖  ✅ 完成：A1 → B1（红）                                │
├─ 输入行 ────────────────────────────────────────────────┤
│ [🎤 空格说话] [ 说点什么… ] [解析]        [ 停止 ]        │
├─ 可执行指令（点一下填进输入框） ────────────────────────┤
│ 搬运 │ 把A区第1行第1列放到B区红列 · B区全部矩形随机摆放回A区 │
│ 查询 │ A区第1行第1列是什么颜色                            │
│ 流程 │ 开始分拣 · 暂停 · 继续 · 停止执行                   │
│ 安全 │ 急停                                              │
└─────────────────────────────────────────────────────────┘
```

**消息类型**（前端本地内存，**不落库** —— 刷新即清，避免"历史消息误导现场"）：

| 类型 | 出现时机 | 内容 |
|---|---|---|
| `user` | 用户说/打 | 原文 |
| `ai` | 回应 | 模板化文本（可解释、不编造） |
| `plan` | 解析成功 | 计划卡（动作/起点/目标/件数）+ 按钮 + **"或直接说：执行"** |
| `run` | 执行中 | 进度气泡（**节流 500ms**，避免刷屏） |
| `result` | 结束 | 成功/失败 + 原因（原样用后端文案） |

### 3.2 R3：语音说"执行"就直执

**判定顺序（顺序本身就是安全设计）**：

```
语音/文字定稿
   │
   ├─ ① 当前有"待确认计划"？ ── 否 ─→ 当作新指令 → 解析 → 回显（进入待确认）
   │                          └ 是
   ├─ ② 是确认词？（执行/开始/确认/跑/go）── 否 ─→ 当作新指令（走上面的分支）
   │                                        └ 是
   └─ ③ ★ 立刻执行该计划（不点按钮）
```

**安全边界（三条，缺一不可）**：
1. **确认词只在"有待确认计划"时才执行** —— 没计划时说"执行"→ 回"请先告诉我要做什么"，绝不瞎跑
2. **确认词表刻意收窄**：`执行 / 开始 / 确认 / 跑 / go`。
   ★ **不收** "好 / 嗯 / 可以 / OK" —— 这些在闲聊里太容易脱口而出（现场讲一句话顺带说个"好"就动了机器，不可接受）
3. **执行前在对话里回显**"正在执行：<计划摘要>" —— 保证可追溯，出问题能查

### 3.3 R4 ★ 执行中被打断 → 回起点 → 执行新指令（**本方案的核心**）

**语义定义**（与既有口径保持一致，不新发明）：

| 事件 | 行为 |
|---|---|
| 用户说"停" | **步边界取消** → **回开始/结束点** → 停在起点待命 |
| 用户下达新指令 | **步边界取消**当前 → **回起点** → **自动执行新指令** |
| 用户连续说多条 | **只保留最后一条**（pending 覆盖），避免堆积 |

> ★ **不是急停**：运动/吸放**中途不停**（那是急停的语义，会甩件）。
> 走的是既有 `request_cancel()` 通道，与分拣页"停止"完全同一套。

**后端机制（新增"接管"）**：

```
POST /ai/exec {plan_id, takeover: true}
   │
   ├─ 空闲 ────────────────────────→ 直接启动（原逻辑不变）
   └─ 正在跑 ─→ ① 记 pending = 本次计划
                ② request_cancel()          ← 复用既有通道
                ③ 立即返回 {queued: true}   ← 不阻塞 HTTP
                          │
   旧 job 的 _run 走到步边界 → 取消 → 回起点（**既有行为**）
                          │
   旧 job 线程 finally ─→ 检查 pending → 自动启动新 job
```

**为什么放在后端而不是前端编排**：
- 前端轮询判断"跑完了没"再发下一条 —— 刷新页面/断网就丢，且多一次往返不"丝滑"
- 后端 `_run` 的 `finally` 是**唯一可靠的"回到起点完成"时刻** ✓

**并发安全**：pending 的读写与 `_job` 共用同一把 `_gate` 锁（现有模式）。

### 3.4 R6：空格键说话

```
keydown(Space) 且 焦点不在 input/textarea
   ├─ ASR 未启动 → 启动（开始说）
   └─ ASR 已启动 → 停止（定稿）
★ preventDefault() 防止页面滚动
★ 焦点在输入框内 → 不拦截（照常输入空格）
```

HUD 与对话区首条提示都写明"**按空格说话**"，避免现场不知道。

### 3.5 R2：可执行指令提示（按能力分组，覆盖全部 5 类意图）

| 组 | 示例 |
|---|---|
| 搬运 | 把A区第1行第1列放到B区红列 · 把A区第1行第1列放到B区第1行第1列 · B区全部矩形随机摆放回A区 |
| 查询 | A区第1行第1列是什么颜色 · B区第1行第1列是什么颜色 |
| 流程 | 开始分拣 · 暂停 · 继续 · 停止执行 |
| 安全 | 急停 |

★ 这些**全部来自 `nl_intent.INTENTS` 的真实能力**（有回归脚本从后端源码解析断言），
不写"看着像支持但实际不支持"的示例 —— 那会让现场白试一次。

## 4. 设计评审与优化（初版 → 优化版）

| # | 初版想法 | 问题 | 优化后 |
|---|---|---|---|
| 1 | 确认词放宽到"好/嗯/可以" | 闲聊里的口头语就动机器，**不可接受** | 收窄为 `执行/开始/确认/跑/go` |
| 2 | 前端编排"接管"（cancel → 轮询 → 再 exec） | 刷新/断网即丢；不丝滑 | **后端 `_run.finally` 自动接力** |
| 3 | 进度每帧写进消息流 | 刷屏、页面抖 | **节流 500ms + 同一气泡原地更新** |
| 4 | 对话历史落库 | 刷新后旧消息还在，**现场会误以为还在跑** | 仅内存，刷新即清；并明确标注 |
| 5 | 新指令直接打断当前动作 | 运动中急停会甩件 | **步边界取消**（与分拣页同一语义）|
| 6 | 多条指令排队依次执行 | 现场等一串旧命令跑完，不"丝滑" | **只保留最后一条**（pending 覆盖）|
| 7 | 把解析结果卡删掉改气泡 | 丢掉"可核对"这一层 | **保留计划卡**（它正是确认的对象），只是搬进对话流 |

## 6. 安全红线（必须守住）

1. **不绕过任何既有闸门**：控制令牌、真实下发总闸、围栏互锁、轴锁、速度口径 —— 全部照旧
2. **不新造运动原语**：接管只是"取消 + 排队 + 复用既有 exec 路径"
3. **急停优先级最高**：`estop` 不排队、不接力，永远立即执行
4. **接管时机的诚实表达**：界面要说明"当前动作跑完才停"（不是立刻停），
   否则操作员会以为一点就停
5. **真机运行期间**：改完先在**空跑**模式演练，再上真机

## 8. 明确不做（范围边界）

- ❌ 不引入大模型做对话生成（保持规则解析可解释；LLM 仍只在规则失败时兜底）
- ❌ 不改判色 / 运动 / 分拣链路
- ❌ 不做消息持久化与多端同步
- ❌ 不做"运动中立即停"（那是急停的语义，会甩件）
- ❌ 不改分拣页（本次只动 AI 执行页）
