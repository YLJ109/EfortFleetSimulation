## 1. 为什么是这几批（现状缺口，全部带证据）

### 1.0 ★ 现场物理构型（负责人 2026-10-12 澄清 —— 这一条直接改写了本方案的三项设计）

> **机器人本体上没有相机。地面上有一只固定相机，只有当机器人把物体送到相机上方（`C检测` 位）时才能判颜色。**

代码侧完全对得上，不是新信息而是**我一直没当真**的信息：

| 事实 | 证据 |
|---|---|
| 判色必须"送到检测位" | `backend/app/services/sorting.py:58 CAMERA_POINT = "C检测"` · `:554` 点位角色表「C检测位」 |
| 检测是**位基**（fixed-camera）而非**眼在手** | `:37-40` 现场口径：吸住 500ms 内取 3 帧（帧间隔 0.15s）、**到 C 检测位停 500ms** 等机械停稳避免拖影 |
| 判色区域是**固定的小图 ROI** | `camera/camera_service.py:412 self.roi = (x,y,w,h) 小图坐标` · `:1145 _norm_roi` · `:1167 set_vision_config(roi=…)` |
| 相机看到的是**当前朝向镜头的那一面** | 双面口径 `faces_for_capture`（先正面→后反面各送检一次，AGENTS.md §5） |

**因此，本方案原先三项设计前提不成立，已当场改掉（不是修补，是换目标）**：

| 原条目 | 原前提 | 澄清后的事实 | 处理 |
|---|---|---|---|
| **D1 相机视野覆盖体检**（把 18 料位投影进判色区，指出"哪一格不可靠"） | 相机能看见料区 | **看不见**。相机只管检测位 | ✗ **作废**，改写为 **D1′「送检链路体检」**（见 §6 D1′） |
| **A4 相机人机在场检测**（虚拟围栏） | 相机能看见工作区周围 | 视野只有一个 ROI，不看人活动区 | ⚠ **降级为"需硬件"**：要么加装/改位第二只相机，要么整项挂起（见 §3.A4） |
| **E5 视觉引导"看一眼就到"**（相机识别料块 → 雅可比补一小步） | 相机能看见待抓工件 | **完全不可能**：视觉唯一能给的是"检测位上那一件的颜色"，**给不出工件位置** | ✗ **整项重写**为 **E5′「固定相机反用法」**（见 §6.5 E5′） |

**同时，这条事实送来了一个更好的创新点**：既然**所有颜色证据都必须经过同一个"咽喉"（C 检测位 + 固定 ROI）**，
那就把这个咽喉本身做成可自证的 —— 判色前先问"这一帧可信吗"（到位偏差、停稳、ROI 内位置、背景/光照漂移），
判色错时能分清**"色带不对"还是"根本没送到位/送歪了"**。
§5.4 早就要求"'检测不到'要分清两类原因"，但今天**没有任何机制能分清** —— 这就是 E5′。

**还有一条必须一起记住的推论**（很多人会漏）：
> 因为工件是在**吸盘上、悬空、被相机从下方拍**，所以**判色的输入几何 = 工具长度 + 吸盘姿态 + 到位精度**。
> 这三者里有两个今天都是"未知/靠推断"（§7：末端工具真实长度未知、持件状态是流程推断）——
> 所以 D3（工具长度实测）与 E2（到位残差）**不是锦上添花，是判色可信度的直接前提**。

### 1.3 UI/UX：颜色语义过载 + 报警无管理

- 七色识别 / 三色分拣 / 围栏四态 / 井字棋 O·X / 料块 / 残影 A·B 全在用颜色表达不同东西，
  **没有一份唯一颜色语义表**；工业 HMI 标准（ISA-101 / IEC 63303）的口径恰好相反：
  **灰阶为底，颜色只用来标记异常**。
- **无报警优先级 / 聚合 / 抖动抑制 / 搁置**概念（`events.py` 只有 `level`），
  现场一旦出现传感器/链路抖动就是"报警刷屏"，操作员会开始忽略报警 —— 正是 EEMUA 191 /
  ISA 18.2 定义的 alarm flooding 失效模式。

  "速度电脑≠实际"的两条命令排查法（`40103` vs `40003`）**没有在界面上呈现**。

### A1 服务端独立安全评估（把围栏权威从浏览器搬到后端）

**痛点**：§1.1 —— 围栏算在浏览器，后端互锁依赖浏览器 1s 上报。

**目标**：后端**自己**每拍算出净空与分级；浏览器上报降级为"一路传感器"，
脚本/第三方客户端/浏览器崩溃三种情况下互锁依然成立。

**做什么**
1. 新增 `backend/app/services/safety_eval.py`：
   - 连杆包络模型：6 段**胶囊体**（线段 + 半径），参数来自
     `config/robot.yaml: safety.links: [{from_joint, to_joint, r_mm}]`；
     ★ **第五轮核实：这个键今天不存在**（`config/robot.yaml` 里 `links/radius/clearance` 零命中）——
     要**新增**，初值由前端 `robot/robotModel.js` 现有几何换算（同一份 DH），
     **并需现场卡尺复核外径**（给数之前只能当"保守近似"，宁可偏大不可偏小），
     配置注释里写明"包络为**近似外扩**"。
   - 用 `kinematics.py:31 _dh_matrix / :103 fk_matrix / :160 joint_axes` 逐关节算各段两端点世界坐标；
     FK 结果与前端 `three` 场景**必须同坐标系口径**（`three/sceneCoords.js` 是 mm→m 的唯一换算，
     后端以 mm 为单位、原点=底座安装面中心、+Z 向上，与 DH 一致）。
   - 几何：`refFloorY`（站台台面高度，前端 `manager.js:314 baseLiftY()` 同源，
     后端从 `config/robot.yaml` 读同一个值）、围栏六面（沿用 `safety_config.py` 的分区）。
   - 判据函数 `evaluate(joints_deg) -> {state, zone, clearance_mm, per_link:[...]}`，
     阈值直接复用 `classifyGround` 的 **warn 150 / danger 80 / hit 30 mm**（前后端已有同源）。
   - **地面净空口径必须与刚修的 bug 同源**：`净空 = 各连杆最低点 − refFloorY`，
     且只取 **J1 以上子树**（前端 `manager.js:305 getGroundRoot()` 就是这个语义）。
2. 采集器每拍调用（`services/collector.py` 已有实时关节快照），结果写入
   `safety_guard` 的**服务端记录**（新增 `source="server"` 一路）。
3. **双源合并 = 取更严重**（fail-safe 保守）：
   `combine(client, server) → 严重度 max`；顺序 `safe < warn < danger < hit`；
   一侧缺失/过期不影响另一侧；快照里**如实带上** `sources: {server: {...}, client: {...}}`。
4. `guard_check()` 使用合并结果；`motion.require_live_safety` 语义不变。

**不做什么**
- 不声称这是安全功能（无安全 PLC、无认证）；界面与文档都写"软件级互锁，不替代控制器安全板"。
- 不改前端围栏算法（前端仍要做，因为它是操作员**唯一看得见的**那一份）。
- 不做碰撞检测（不判机器人 vs 工件/夹具），只做"围栏 + 台面净空"。

**唯一判据与口径**：`safety_eval.evaluate()` 是唯一的服务端实现；
`safety_guard` 是唯一互锁入口。★ **第五轮核实（含对上一版自查的纠正）**：
后端**已经有完整的围栏配置** —— `app/core/safety_config.py`（`default_safety()`/`validate_safety()`，

### A2 轨迹扫掠前瞻（"路上"安全，不只是"终点"安全）

**痛点**：现在只量单一目标位姿（`manager.js:341 withTarget`）。

**目标**：对任意一段运动 `q0 → q1`，给出**最小间隙出现在第几个采样帧**、
该帧哪根连杆、以及**建议抬升高度**（若中段触及台面/围栏）。

**做什么**
1. `safety_eval.sweep(q0, q1, mode="joint", n=48)`（**纯函数、离线**）：
   - 插值口径与显示层一致 —— 前端 `manager.js:424 stepSmoothing`（k=14/s）是"显示平滑"，
     前瞻用**等分关节线性插值**并在注释里写明"这是保守包络估计，不是控制器真实轨迹"。
   - 每帧 `evaluate()` → 得 `min_clearance` 曲线；输出
     `{ok, worst_frame_idx, worst_mm, worst_link, curve[], lift_suggest_mm}`。
   - `lift_suggest_mm` = 使 worst 达到 warn 阈值所需的最小整体抬升（把 J1..J6 的
     平移解算成"底座/站台抬高量"，与 `refFloorY` 同口径）。
2. 界面（残影路径染色）：`ghost.js` 增加"路径带"（采样帧链的细线 + 逐段染色：
   绿=安全 / 黄=接近 / 红=危险），**沿用现四态配色**，不新增颜色语义。
3. 复用点：`/sorting/goto` 的**原位安全路径**多段（`services/sorting.py: raw_slot_safe_path`）
   每段都跑一次 sweep，回执里带上 `sweep` 摘要 → 界面日志"第 2 段最小间隙 43mm（接近）"。

**不做什么**
- 不做时间最优轨迹 / 不加减速规划（那是控制器 210 的事）。
- ★ **第五轮核实补充**：**给不出"还有几秒到达"** —— PC 只写目标 + 触发位，控制器不回报进度，
  采样也只有 10Hz（`config/robot.yaml:98 sampling.read_hz`）。
  所以 sweep 只回答"**这条路径上有没有侵入、最险在哪一格姿态**"，
  界面**禁止**出现"预计 2.3s 后侵入"这类时间表述（§5.5 铁律⑤：假功能/大话要么接线要么删）。
- **不自动修改目标点位**（CBF 式"只修正不改变意图"在这里退化为"只提示"）。
- 不做多步（跨段）动力学预测。

**接口**：`POST /api/safety/sweep`（入参 q0/q1 或点名对，纯计算，无下发）；
`/sorting/goto` 回执加 `sweep` 字段（**只加字段，不改语义**）。

**回归钉**：`tests/test_safety_sweep.py::test_midpath_dip_is_detected_even_when_endpoint_is_safe`
（终点安全、中段扫到台面 → 必须报 danger）、
`test_lift_suggestion_makes_path_pass`、`test_sweep_never_issues_motion_commands`
（静态断言：该模块不 import motion.command / 不调 modbus 写）。

**工作量**：4 天。**优先级：P2。**
**度量**：能覆盖"到点没撞、路上撞"这类事故（现状完全不可见）；预演耗时目标 < 30ms/段
（★ **这是目标值、不是实测值**：48 帧 × 每帧 6 段胶囊 FK，本地计时确认后再写进界面/文档）。

### A3 SSM 式动态限速**建议**（只做提示，绝不做闭环）

**目标**：按 ISO/TS 15062 的 `S = K·T + C` 给出**建议速度上限**，
让操作员知道"现在这个速度对应的分隔距离是多少、够不够"。

**做什么**
1. `safety_eval.ssm_advice(distance_mm, speed_pct, cfg)` →
   返回 `{required_speed_cap_pct or None, separation_mm, inputs: {...}, unknown: [...]}`。
2. **参数缺失就返回 None 并如实列在 `unknown` 里**（铁律③：未知不得塌成布尔 / 不得编数）：
   - `T`（总停机时间 = 检测+响应+制动）**必须现场实测**才填；
   - `K` 由 `T` 与速度换算导出；`C` 取配置。
3. 界面只出现在"速度"卡片旁：**「建议 ≤ X%（分隔 S=…mm；T 未实测 → 无法给出）」**。

**不做什么**
- **绝不写 40103、绝不动滑块**（速度唯一口径 = 右上角滑块，AGENTS.md 明文）。
- 不做自动降速、不接入 `ui_speed`（那个模块的唯一写入者仍然是前端滑块）。
- 在 `T` 未实测前，界面必须显示"无法给出"（不许显示"安全"）。

**回归钉**：`test_ssm_advice_returns_none_when_brake_time_unmeasured`（默认配置必须返回 None）、
`test_ssm_never_writes_speed`（源码静态断言：不出现 `ui_speed.publish` / 40103 写）。

**前置依赖**：现场制动时间实测（可由 `tools/rc_speed_audit.py --run` 扩展一个"停机计时"，
**必须负责人同意后才跑真机**）。**工作量**：2 天（+ 实测 0.5 天）。**优先级：P2（依赖现场数）。**

## 6. D 批 · 摆放（几何与布置的自证）

### ~~D1′ 送检链路体检~~ —— ★ 第六轮**撤回**（负责人：现场摆放没问题，见 §10.4；正文保留只为记录"想过又撤"）

> ★★ **为什么原来的 D1 是错的**（负责人 2026-10-12 澄清 + 代码证实）：
> 相机在地面、只对 `C检测` 位（`sorting.py:58`、`:554` 点位角色「C检测位=举件停留处」），
> **根本不看 18 个料位**。所以"把 18 料位投影进判色区、指出哪格判色不可靠"这个前提**不成立** ——
> 料位从来就不在视野里。判色的可靠性**不取决于料位**，而取决于**送检这一段**：件举到 C 检测位时
> 有没有停稳、有没有正对镜头、有没有把朝下的那个面**完整送进 ROI**。

**体检对象换成"送检链路"（这才是本项目里唯一真正影响判色的几何）**
- **输入**：`C检测` 示教位姿 + 相机 ROI（`camera_service.py:412 self.roi`）+ 相机高度
  （`sortingBlocks.js:370 camera_height_mm`，0=坐在台面）+ 件尺寸（现 70×70×14）+ DWELL_MS。
- **算三件事**（全部离线纯几何，用 `kinematics` FK）：
  1. **停留充分性**：`到 C 后停留 DWELL_MS(500ms)` 内机械是否真停稳 —— 结合 E2 的到位残差曲线，
     若 500ms 时残差仍在收敛 → 标"取帧可能带拖影"（现场口径明说"避免拖影判错"）。
  2. **投影视野**：件在 C 检测位、**当前这一面**（正/反取决于 J6，`faces_for_capture`）
     投影到相机像平面 → 是否**完整落在 ROI 内**、占比多少、四角是否出框。
     件歪了 / 半出 ROI = 判色错的高发原因，而这**从来没有被体检过**。
  3. **两面一致性**：正面送检与反面送检（J6−180）投影中心是否落在 ROI 同一处
     （反面偏出 ROI → "反面检测不到"其实是**没对准**，不是没颜色）。
- **输出**：一张"送检体检表"：C 位到位停稳裕度 / 正面投影覆盖率 / 反面投影覆盖率 /
  建议（"ROI 需放宽到 …"或"C 检测位需重录：当前件心偏离镜头中心 X mm"）。
- **直接服务 §5.4 那条硬要求**："'检测不到'要分清两类原因（物体超出画面 vs 真漏检）" ——
  本项**就是把这两类分开的几何依据**（投影出框 = 前者，停稳/ROI 正常却判不出 = 后者）。
- **不做什么**：不去"看料位覆盖"（相机做不到）；不改 ROI 配置（只建议，由人确认）；不接相机实测（先纯几何给结论）。

**回归钉**：`verify_cam_delivery.mjs`（纯几何：件歪 5mm → 投影覆盖率下降可测；反面偏出 ROI 能被标记）。
**工作量**：2.5 天（比原 D1 小，因为不用处理 18 格）。**优先级：P1（判色可信度的真正咽喉）。**

### E1 意图编译器 —— 自然语言不直接"驱动机器人"，而是先编译成**一份可否决的路径计划**

**现状证据**
- 已有自然语言/语音入口：`backend/app/services/nl_intent.py`（规则）+ `llm.py`（大模型兜底）+ `asr_tencent.py`（语音字幕），AI 执行页已对话化。
- 已有安全路径模型：`services/sorting.py: raw_slot_safe_path`（原位→正上位→目标正上位→目标）+ 未就绪闸门 + J6 旋转闸门。
- **缺口**：解析结果是**直接进流程执行**的；操作员看不到"这句话会变成哪几段动作、每段间隙多少"，只能在事后从日志里回看。

**创新点（新在哪）**
把 LLM/规则的输出**降级为一个"意图 AST"**（中间表示，不是指令），再由**确定性编译器**产出
`计划 = [{段, 目标点, face, 气路动作, 闸门结论, sweep 最小间隙, 预计耗时}]`，
界面先展示这份计划、**由人按下执行**，执行时逐段自证。
→ 这正是 KTH 论文《Agentic Neuro–Symbolic Planning and Commissioning for Human-in-the-Loop Industrial
Robotics with Digital Twins》（LLM 管语言与上下文、**符号层保证物理可行**、人在环）
与 OWASP Top 10 for Agentic AI 的「**preview before effect / separate preview from effect**」两条口径的落地形态；
而目前市面上的机器人网页监控产品普遍没有把"一句话 → 可审计路径计划"这条链闭合。

**做什么**
1. `backend/app/services/intent_ast.py`：解析结果规范化成 AST（动作、对象、槽位、面、次序）；
   **字段缺就缺**（不许 LLM 补默认值 —— 铁律③）。
2. `services/intent_plan.py::compile(ast, live, layout)` → 计划列表；每段调用
   `raw_slot_safe_path` + `effective_face` + `safety_eval.sweep`（A2）；
   任一段被闸门判为不可行 → **计划整体标红并指出是哪一段**，而不是"跑到那儿再失败"。
3. 界面（AI 执行页新增"计划卡"）：分段列出 + 每段间隙/耗时/面 + 「执行 / 改一个参数重试 / 放弃」；
   计划本身进 A5 取证存储（可导出、可复盘）。
4. **降级路径**：LLM 不可用时，规则解析（`nl_intent`）单独也能编译出计划。

**不做什么**
- **LLM 不得决定**：速度（唯一口径仍是右上角滑块）、气路位号（唯一来源仍是 `modbus.VAC_ACTIONS`）、
  面语义（仍由 `keep`/`front`/`back` 派生）、是否绕过闸门。
- 不做"LLM 安全评审员否决闸门"（幻觉会误拦停线）；LLM 只写解说文字，**没有否决权也没有指令权**。
- 不做开放式工具调用（不给 LLM 任意 REST 权限）。

**唯一判据**：`intent_plan.compile()` 是"意图 → 段序列"的唯一实现；流程里不许再排一遍顺序
（与既有 `faces_for_capture` / `order_for_drop` / `order_for_restore` 唯一判据共存、不覆盖）。

**接口**：`POST /api/ai/plan`（只编译，不动作）· `POST /api/ai/plan/{id}/execute`（经现有闸门）。

**回归钉**：`tests/test_intent_plan.py`：
`test_llm_never_emits_speed_or_vacuum_bit`（AST schema 里根本没有这两个字段）、
`test_plan_marks_infeasible_segment_before_execution`、
`test_plan_compile_works_without_llm`、
`test_execute_entry_passes_existing_gate`（静态断言：执行入口必过 `reject_if_not_ready` + `guard_check`）。

**工作量**：5 天（依赖 A2；无 A2 时先出"段 + 闸门结论"，间隙列留空并如实标注）。**优先级：P1。**
**度量**：真机"跑错了才发现"的次数↓；真实下发中"事前有可审计计划"的覆盖率（目标 100%）。

### E2 到位自证（段级残差带 + 时间窗判据）—— 孪生从"画面好看"升级为"机器没按你以为的路走就报警"

> ★★ **第五轮自查：本条原稿标题「逐帧自证孪生 / 期望轨迹 vs 实机的跟踪残差」写得比实际能做的更满，已当场降级。**
> 两条硬事实（都已核过代码）：
> 1. **我们没有"期望轨迹"的时间基准** —— 执行者是控制器里的常驻程序 210（§4 机理），
>    PC 只写"目标数据 + 触发位"，**拿不到速度曲线/加减速规划** → 无法逐拍算"此刻应该在哪"。
>    能算的只有**段级**量：`|q_actual − q_target|`（目标点已知、回读确认过）随时间的**收敛过程**。
> 2. **采样上限 = 10Hz**（`config/robot.yaml:98 sampling.read_hz: 10.0`，推送 20Hz 但那是同一份读值复用）
>    → 一拍 100ms，本身就带 ±100ms 的时延不确定度。
> **因此终版口径**（不是"跟踪残差"，而是**四件事都能自证**）：
> ① 下发后 T_start 秒内**动没动**（`stuck`）；② **峰值残差**与**收敛耗时 settle_ms**；
> ③ **到位后是否回弹/过冲不回**（`overshoot`）；④ **超时无进展**（`not_reached`）。
> 界面与文档一律写成"**到位自证**"，**不出现"轨迹跟踪精度"**这类说大话的字（§5.5 铁律⑤）。

**现状证据**
- 全仓 grep `残差 / residual / tracking_error` **零命中**；
  姿态权威模型只解决"**该显示哪个来源**"（`stores/robot.js: displayQ` + `App.vue:401-427` 全站唯一下发点），
  **没有"期望 vs 实际"的一致性检查**。
- `manager.js:424 stepSmoothing`（k=14/s）只服务观感。

**创新点**
把已有的两份数据 —— 我们**下发并回读确认过的目标** ↔ 采集器**每拍实测的实时关节** —— 做成段级残差：
`res_i = |q_actual,i − q_target|`（J6 取环形最短弧），
得到每条动作的**残差收敛曲线** + 到位时刻 + **超差即事件**。
→ 这把 AGENTS.md §4 那条硬机理「**下发成功 ≠ 动作完成，必须看完成位**」
从"检查一个完成位比特"升级成"**整段过程持续自证**"。
这是本项目核心主张「不做能连上的远程控制，做每一步都能自证的远程控制」最直接的量化形态，
也是同类网页监控产品里没有的东西。

**做什么**
1. `backend/app/services/twin_residual.py`：维护"当前在飞的期望段"（取自 `motion.command` 的回读值），
   与采集器每拍实测做差，输出
   `{max_mm_deg, settle_ms, profile[], verdict: ok | slow | overshoot | stuck | not_reached}`。
2. 界面：动作卡片加"残差条"（当前值 + 峰值 + 目标带）；3D 把**超差段**的轨迹线染色；
   超差 → `events.emit("twin","warn","residual_over", …)`，连续超差 → 显示"建议暂停"
   （**不自动暂停、不自动重试** —— 刹车必须人点，也不许打断真机流程）。
3. 与 A5 取证包打通：每次 danger/hit 自动带上"当时正在飞那一段的残差曲线"。
4. **诚实边界**：到位容差与采样延迟造成的表观残差必须显式建模成"不确定带"（显示 `±X`），
   不能把采集滞后说成"机器不准"（铁律③）。

**不做什么**：不做闭环控制（PC 只能写目标 + 触发位，执行者是控制器里的常驻程序 210）；
不据此自动改速度/重试；不做振动与动力学建模。

**回归钉**：`tests/test_twin_residual.py`：
`test_stuck_arm_is_detected`（目标变了、实测不动 → `stuck`）、
`test_sampling_lag_alone_is_not_flagged`（只加延迟不加偏差 → 仍在不确定带内）、
`test_j6_ring_difference_is_shortest_arc`、
`test_never_emits_auto_stop`（源码静态断言：不出现急停/取消运动调用）。

**工作量**：3 天。**优先级：P1 —— E 批里性价比最高、且完全只读。**
**度量**：「显示到位、实际没到位」从"靠人眼发现"变为**自动 ≤1s 发现**；
每条动作都有可导出的**过程证据**（而不只是完成位那一个比特）。

### E3 反事实试跑（What-if 沙盒）—— 不碰真机，回答"这样改会怎样"

**现状证据**：预演只算**单一终点**（`manager.js:341 withTarget`）；无节拍估计、无参数扫描、无概率。

**创新点**：把 `kinematics` + `safety_eval.sweep`（A2）+ 点位库 + 既有约束求解
（逐格约束 / 同色成行成列）组成一个**离线实验台**：
对 {摆放偏移、速度档、面策略、取放次序} 做参数扫描 + **蒙特卡洛抖动**
（抖动源 = 到位容差、采集噪声、判色置信度、制动不确定度），
输出**分布**而不是单点：节拍 P50/P90、最小间隙分布、"哪一段最可能不到位"的概率。
→ 对标 AnyLogic「数字孪生按实时数据初始化后跑 Monte-Carlo / Parameter Variation 实验」、
KUKA iiQWorks.Sim 与 3DEXPERIENCE 的 what-if 场景验证；
**本项目的独特实现路径**：不引入任何仿真引擎、不需要真机，纯 numpy 在现有函数上跑 ——
现场换型前 30 秒就能自证"这套摆放值不值得上真机"。

**做什么**
1. `services/whatif.py::run(scenario, n=200, seed)` →
   `{cycle_time_p50/p90, min_clearance_dist, worst_segment_prob, failures[], jitter_sources[]}`；
   ★ **第五轮核实：`n=200` 目前是**未经计时**的数字** —— `ikine`（`kinematics.py:210`）是 numpy 数值迭代，
   一趟约 10 段 × 200 样本的真实耗时现在**算不出来**。
   **实现第一步就是跑一次离线计时**（单样本 ms 级），据结果三选一：`n` 降到 50 / 改后台任务 + 进度 /
   用 `fk_matrix` 几何扫掠代替完整 IK。**界面上的样本数必须等于实际跑出来的那个**（铁律②）。
2. 界面并入「摆放体检」页（与 **D1′/D6/D2** 同一页）的"实验台"标签：改参数 → 出直方图/箱线 +
   一句结论（例：「B 区右移 10mm：最小间隙 P5 = 31mm（危险），不建议」）；
3. 结果落到 A5 同一存储路径，可导出、可与"上一次实验"对比。

**不做什么**
- **不自动优化下发**（不改点、不改速度、不改次序）—— 只给分布与建议，决定权在人。
- 不声称仿真精度；所有输出必须带"离线统计估计 · 非认证"与实际使用的抖动来源清单。
- 不引入新第三方仿真依赖。

**回归钉**：`tests/test_whatif.py`：
`test_whatif_never_touches_motion_or_modbus_writes`（★ 核心静态钉）、
`test_jitter_sources_are_listed_in_output`、
`test_shifted_tray_lowers_min_clearance_p5`（构造用例证明方向正确）。

**工作量**：4 天（依赖 A2）。**优先级：P2。**
**度量**：换型/重录点前的可行性判断，从"占真机半小时"降到"离线 30s"。

### E4 现场自学习判色闭环 —— 让阈值由现场证据自己长出来（**每次改动都要人确认**）

**现状证据**：`camera/vision_color.py:1436 class ColorSampler` 已实现但
**尚未接线到判色链路与界面**（AGENTS.md §7 明文"进行中"）；现阈值 0.55 来自现场实测最低 0.67；
七色中橙/黄/青/紫仍无色卡实测。

**创新点**：**把操作员每一次"改判 / 无效色放回"变成一条免费标注样本**，
用 `ColorSampler` 聚合 → 给出"色相带该怎么挪"的**建议补丁** →
经确认后写入、可一键回滚、且**必须先跑一次现场真图回放回归**才允许生效。
→ 同类系统要么把阈值当配置手填（漂移无人知），要么黑箱自适应（不可解释）；
本项目做的是**「证据 → 建议 → 人确认 → 回归 → 生效」的可审计学习环**，
正好把 §5.4「判色阈值只能按现场实测值定，不能按合成图定」这条口径**产品化**。

**做什么**
1. 视觉服务侧：每次判色把 ROI 特征 + 判据值写入样本环（落在 `EFORT_LOGS_DIR` 下，遵守隔离纪律）；
   人工改判/放回事件（已有流程）作为标签回流。
2. `camera/vision_advice.py`：按色统计混淆与置信分布 → 输出**建议 diff**
   （例「青：`fill_min` 0.55→0.58，样本 n=37，误判 3 次」）；
   **n 不足（如 <20）就不给建议**。
3. 界面「判色体检」卡片：每色的样本数 / 置信分布 / 建议；
   「应用建议」= 展示 diff + 跑 `camera/tools/vision_e2e_replay.py` + 通过才写配置；保留上一版可回滚。
4. 橙/黄/青/紫在样本不足时**永久显示"未标定"**，不许被"学习"自动填上。

**不做什么**：**硬安全相关阈值不参与学习**（黑暗判据 `dark_chroma_max` / `dark_s_max` 只能人显式改并留档）；
不自动改配置；不因学习而放宽"物体超出画面 vs 真漏检"两类原因的区分。

**回归钉**：`camera/tools/vision_color_test.py` 扩展（样本环与建议派生的纯函数）+
`tests/test_color_advice.py::test_advice_requires_sample_count` /

**工作量**：4 天。**优先级：P1（§7 明文限制的唯一根治路径）。**

### E5′ 固定相机反用法 —— 把"只能判色的一只朝上相机"变成**零成本量测基准 + 持件证据**

**现状证据**：录点靠示教器/点动；§7 明文两条"未知"（末端工具真实长度、持件/落料状态只是流程推断）；
判色只用了一次（`sorting.py:37-40` 到 C 位停 500ms 取 3 帧）。

**创新点（这条是被现场约束"逼"出来的，反而比原来的"视觉伺服"更成立、更值钱）**
现场只有一只**固定在地面、只对 C 检测位**的相机 —— 它**不能**看料区、**不能**做抓取引导，
但它有两个被浪费的性质：
1. **位置已知且永远不动** → 每一次"举件到 C"都是一次**对同一参考点的重复测量**；
   于是**判色用的那几帧，本身就是到位精度的证据**（件心在 ROI 里的位置、件底离镜头高度）。
2. **正对件被吸着时朝下的那一面** → 那一帧里"有没有方块"直接就是**"吸住了没有"**的观测值，
   而现场根本没有真空传感器。

把它做成功能：**同一批帧，第一次被用两遍** —— 判色之外，再产出三个此前拿不到的量：
- **持件/落件证据**（帧内块面积/中心稳定 = 吸住了；吸后仍空 = "吸空"）→ 把 §7"纯流程推断"
  升级为**有观测值的推断**，并**如实标注依据**（铁律②：口径以证据为准）；
- **到位复现性漂移**（按来源格分组统计件心分布 → 某格系统性偏了 = 该格示教姿态漂移）→ **建议重录哪一格**；
- **工具有效长度反推**（吸盘底离镜头距离 = 示教 Z − FK 件底 − 件厚 → 中位数）→ 攻 §7"末端工具真实长度未知"。
→ 关键：**不加任何硬件、不多拍一帧、不动机器人**，只是把已有帧信息榨干。

**做什么**
1. 视觉服务判色那刻顺带产出：`presence{conf,area_px,cx,cy}` + `standoff_mm`（由 ROI 内块尺寸反推，
   依赖已知的件物理尺寸 —— 这正是 §7"料尺寸未卡尺实测"要补的）；`min_interval` 与 ROI 已可配
   （`camera_service.py:1167`），**不新增配置面**。
2. `services/hold_state.py`：吸/放动作**之后**做一次 C 位检测（真实流程本就要去 C），
   持件状态显示三档：**确认（有视觉证据）/ 仅推断（无相机或无证据）/ 矛盾（证据与流程不符）**；
   矛盾 = warn 事件 + 建议停止（**不自动动作**）。
3. `services/tool_metric.py`：逐格件心分布 + 工具长度反推 + 不确定度；**只出建议**
   （"B7 件心系统性偏右上 6px，建议重录"、"L≈42mm±3，是否写入工具配置？"）。
4. **不确定度诚实**：件尺寸/相机标定未实测 → `standoff` 与 `L` 一律带 `±`；拿不到证据只写"未知"，
   **绝不写"无人/无件/已对位"**（铁律③）。

**不做什么**
- ✗ **不做抓取引导 / 视觉伺服** —— 相机看不见料区，物理上不成立（原 E5 因此作废；
  其外部对标 北航学报视觉引导示教 / AnyTeleop / IBVS-PBVS 全部**弃用**，见 §12 注）。
- 不做闭环（单次观测、只读；§5.1「绝不打断真机运行」——**运行期间只读帧内信息，绝不新增移动**）；
- 不自动写工具长度配置（必须人确认，可回滚）；不做 YOLO 目标检测那套（torch 依赖与内存代价，与"榨干已有帧"无关）；
- 不拿"没检测到件"当"安全可继续"的理由（**只做单向收紧**，同 A4 的硬边界）。

**接口**：`GET /vision/last` 增字段（**不动判色结论本身**）；`GET /api/metrics/hold-state`；
`GET /api/metrics/tool-length`。

**回归钉**：`tests/test_hold_state.py::test_no_camera_never_reports_confirmed`、
`test_empty_frame_after_suck_is_contradiction_not_safe`、
`tests/test_tool_metric.py::test_grouped_offset_drift_is_flagged_per_slot`、
`test_standoff_requires_known_block_size`（件尺寸未知 → 不给长度，只给像素量）。

**工作量**：3.5 天（比原 E5 的 6 天小，且**零真机风险**）。**优先级：P1 → 建议升为 E 批第二优先**
（它同时命中 §7 的**三条**已知限制：持件状态、工具长度、料尺寸，且直接提升判色可信度）。

### E6 机器人自述 —— 每天一页"这台机器自己写的现场日报"

**创新点**：把 E2 残差 + A5 取证包 + C2 报警统计 + E4 判色样本量 + D2 点位体检，
汇总成**一页中文日报**（谁、何时、跑了什么、最险的一次间隙多少 mm、哪个点最可能不到位、
今天人工改判几次），可打印贴墙、可归档。
→ 关键定位：**LLM 在这里是"讲解员"而不是"驾驶员"** —— 只读、只写文字、零否决权、零指令权。
守住这条边界，就是同类产品的空白区（多数要么没有日报，要么日报里没有证据链）。

**做什么**
1. `services/daily_report.py`：**所有数字由结构化数据代入固定模板**（事件表 / 取证 manifest / 体检表）；
2. LLM 仅做措辞归纳与"今日三件最该关注的事"排序理由的**自然语言复述**；
3. 出稿前做一次**数字一致性校验**（LLM 文本里出现的每个数值必须能在结构化源里找到同一值）；
4. 界面：「运维」页"今日日报" + 导出 markdown/PDF。

**不做什么**：不生成任何下发；不代替结构化事件；LLM 不可用时**仍出纯模板版日报**（数字齐全、只是没解说）。

**回归钉**：`tests/test_daily_report.py`：
`test_report_numbers_come_from_structured_data_only`、
`test_inconsistent_number_blocks_publish`、`test_llm_cannot_emit_commands`、
`test_report_still_publishes_without_llm`。

**工作量**：2.5 天。**优先级：P2。**

### E7 一格三证 —— 告警在 2D 布局 / 3D 场景 / **送检帧**里同时落到"同一件东西"

**现状证据**：同一格在多套表征里各自描述 —— `pad/PadMap2D.vue` + `pad/nav.js`（20 点）、
`three/sortingBlocks.js`（料块）、判色记录（`camera/camera_service.py` 的 `/vision/last` + records），靠人保持一致。

> ★ **校正（现场构型）**：原先写"相机画面里画框放大该格 ROI"是**错的** ——
> 固定朝上相机**根本拍不到 A/B 料格**（它只看 C 检测位）。所以第三"证"不是"料格的相机画面"，
> 而是**"这件料被送到 C 检测位时的那一帧判色证据"**（`/vision/records` 里已有缩略图）。
> 一个料格的"三证" = **它在 2D 的位置 + 它在 3D 的位置 + 它上一次送检的那帧结论**，三者用 `cellId` 串起来。

**创新点**：引入贯穿三者的**唯一 `cellId`**（由 D5 的 `config/layout.yaml` 唯一派生），
任何报警 / 判色结论 / 残差事件都带 `cellId` →
- **2D 图**：该格闪烁；**3D 场景**：该料块描边；
- 点该格 → 弹出**它最近一次送检的那一帧**（判色结论 + 件心在 ROI 里的位置 + 置信度），
  而不是"去相机实时画面里找一个不在视野里的格子"。
→ 单击完成"定位 + 看孪生 + 看证据帧"；把 AGENTS.md §8 第 6 条排查经验
（**"界面显示与实际不符，优先怀疑渲染层在编故事"**）产品化成"三处一比对立刻看出来"。

**不做什么**：不假装能拍到料格（相机拍不到）；不新增判色、不新增坐标系（`cellId` 只派生自布局）；不做 AR 叠加。
**回归钉**：`verify_one_cell.mjs`（断言 2D/3D 高亮与"送检帧回看"都用同一 `cellId`，来源同一份布局文件）。
**工作量**：2.5 天（依赖 D5）。**优先级：P2。**

### 10.1 第三轮复核（负责人追问"**创新性功能呢？**"之后）

> **先认错**：第一、二稿的 A–D 四批本质上是**加固型**功能（把已有能力做扎实、清零假显示），
> 严格说**不叫"创新"**。追问是对的，缺口在"用本项目独有资产做出别人没有的能力"这一层。
> 因此补写 **§6.5 E 批**。

**这一轮的方法**：先盘点"本项目已经有、但没人接起来的东西"（自然语言/语音入口、
完整 FK/IK/雅可比、残影孪生、判色链 + 未接线的 `ColorSampler`、取证与事件），
再去检索 2024–2026 的同类工作（KTH 智体神经-符号规划、OWASP Agentic AI 的 preview-before-effect、
AnyLogic/KUKA 的数字孪生蒙特卡洛 what-if、北航视觉引导示教编程 1.18mm/RMS 0.47mm 精度量级、
AnyTeleop 浏览器端遥操、Foxglove/Lichtblick 的 MCAP 时间轴回放），
**把外部路线落到本项目的硬口径上**，而不是照搬功能名。
> ★ 上面「视觉引导示教 / 浏览器端遥操」两条**只是检索到、并没有采用** —— 负责人澄清现场只有
> 地面一只朝上相机后，它们连同 IBVS/PBVS/EGM 一整套路线**全部弃用**（见下表与 §12 注）。

**E 批刻意"不做"的创新（写清楚，避免被当成能力不足）**

### 10.2 第四轮复核（负责人纠正现场构型："**机器人本身没有摄像头，地面上有一个，把物体放到摄像头上面才能判色**"）

|---|---|---|

**这轮的方法论收获（写下来防再犯）**：
1. **现场构型是硬约束，不是背景** —— 凡是"用相机"的功能，先问"这台相机**物理上看得见那个东西吗**"，
   一句话能否掉三天的设计。项目里 `CAMERA_POINT`/`camera_height_mm`/`DWELL_MS` 早就写着，**方案该先读代码再做梦**。
2. **约束往往是创新的来源** —— "只有一只朝上的固定相机"这个限制，直接生成了 E5′（把判色帧当量测基准）
   和 D1′（送检链路体检），二者都比我原来"视觉伺服/视野覆盖"的通用套路更贴本项目、更可行、且更值钱。
3. **连带把 E4 也补严了**：判色建议的样本必须带上"**到位残差 + 件心在 ROI 内位置**"两个上下文，
   否则自学习会把"**没送到/送歪**"（几何问题）误当成"色带不对"（阈值问题）去学 —— 那会学出一版更错的阈值。

**因此同步调整**：E4 优先级↑、E5′ 成为 E 批第二优先（P1）、D1′/D6 进 P1、A4 移出路线挂起待硬件。
D3 工具长度与 E2 到位残差被**重新定性**：它们不再是"锦上添花"，而是 E5′/D1′ 判色可信度的**直接前提**。

1. **E3 蒙特卡洛的性能没实测**：`ikine` 是 numpy 数值迭代，`n=200 × 每趟约 10 段` 的耗时我现在**算不出来**。
   → 实现前要先跑一次**离线计时**；超时就把 n 降到 50 或改后台任务 + 进度条。**不能嘴上写 200。**
2. **A1 与前端"两套几何不可能逐位一致"**：前端量的是 GLB mesh 的世界 AABB（`manager.js:609 groundBox.min.y`），
   后端量的是**胶囊近似** —— 必然有差。方案里那条 1mm 交叉核对**有可能天然过不了**，
   那就必须退成"只对齐**分级结论**（state），不强求 mm 相等"，并把差异如实显示。
3. **误报会让整套东西失效**（这是行业老路，EEMUA 191/ISA 18.2）：保守包络 + 10Hz 采样一定会带来误报，
   现场忍不了就会关掉互锁 → 所以 A6 新鲜度、C2 抖动抑制、影子期**不是流程装饰，是这套功能能活下来的前提**。
4. **"安全"这个词在界面上的边界**：所有产出都写"**软件级互锁，不替代控制器安全板 / 无认证**"，
   本方案不声称达到 ISO 10218 的 SSM/PL 等级（§3 A1"不做什么"已写明）。

**一句话答复**：档一（约 15 项）**能实现且安全**；档二（6 项）**代码能实现、数值要现场给**，
不给就只能是"未知"而不是"假精度"；档三是我原稿里 3 处过头的话，**已经改掉了**，
剩下 2 个真未知（E3 的耗时、A1 双源能否 1mm 对齐）**必须先做离线验证再承诺**。
