# 方案-井字棋对弈（机器人真实落子）

> 状态：**待确认**（本文档只做设计，不含实现）
> 提出：2026-10-10 ｜ 关卡：分拣页右侧新增「井字棋」功能
> 前置理解：用户已确认 7 条口径（见 §1.2），本文档据此成稿，**§11 列出仍需拍板的 3 项**

## 1. 一句话

用 A 区的真料当棋子、B 区的 3×3 格位当棋盘，**机器人真机搬运落子**，
用户在屏幕上用键盘/鼠标下井字棋，AI 按难度应对 —— 全部走现有的分拣运动链路。

### 1.1 做什么

| # | 能力 |
|---|---|
| 1 | 屏幕出现 **2D 井字棋**（叠加在分拣页 3D 视口上） |
| 2 | **键盘** ↑↓←→ 移动光标、**Enter** 落子确认；**鼠标**直接点格落子 |
| 3 | 用户落子后，**机器人真实搬运**：从 A 区取对应料 → 放到 B 区对应棋格 |
| 4 | AI 按**三档难度**应对落子，同样真实搬运 |
| 5 | 随机先手；**先手执圆** |
| 6 | 胜负与平局判定清晰；用户赢 → 屏幕特效 + 语音播报（祝贺语） |
| 7 | 右侧「井字棋」卡片：难度选择 / 开始 / **暂停·继续** / 停止 / **复盘** |
| 8 | 无论胜负，机器人收尾**回开始/结束点**（起点） |

### 1.2 不做什么（边界，防止跑偏）

- **不做**第二个 3D 场景 / 第二套棋盘模型 —— 棋盘就是现有 B 区 9 槽，复用 `sortingBlocks` 的摆放
- **不做**独立的新运动链路 —— 一律复用分拣原语（`_move` / `_air` / `RunContext`），**不新造下发通道**
- **不做**判色 —— 棋子符号由"来源格"决定（A1–A5=圆、A6–A9=叉），**不需要 C 检测位**
- **不做**联网对战 / 存档棋谱 / 排行榜
- **不自己造速度** —— 一律沿用右上角全局速度（默认 5%，安全档），见 §7

## 2. 玩法规则

### 2.1 物料 = 棋子（用户口径 5）

| 来源格 | 代表棋子 | 数量 | 用途 |
|---|---|---|---|
| **A1–A5** | **圆**（○） | 5 | 井字棋**先手**最多 5 手 |
| **A6–A9** | **叉**（✕） | 4 | 井字棋**后手**最多 4 手 |

- 5 + 4 = 9，恰好是井字棋一整局的极限用量（先手 ≤5、后手 ≤4），一个不多一个不少
- 物理上是 9 个矩形块，**形状/颜色不强制区分**；圆/叉只体现在 2D 与 3D 的**显示**上（见 §11-②）

### 2.2 棋盘 = B 区 3×3（用户口径 1）

沿用现有 `B_SLOTS` 行优先编号（`services/sorting.py:22`）：

```
棋盘视角（屏幕）            B 区实际槽位
 ┌───┬───┬───┐            ┌────┬────┬────┐
 │ 0 │ 1 │ 2 │  第1行  →   │ B1 │ B2 │ B3 │
 ├───┼───┼───┤            ├────┼────┼────┤
 │ 3 │ 4 │ 5 │  第2行  →   │ B4 │ B5 │ B6 │
 ├───┼───┼───┤            ├────┼────┼────┤
 │ 6 │ 7 │ 8 │  第3行  →   │ B7 │ B8 │ B9 │
 └───┴───┴───┘            └────┴────┴────┘
      cell index i  →  槽位名 B(i+1)
```

### 2.3 先后手（用户口径 2）

- **随机先手**：开局掷一次，用户先或机器人先
- **先手执圆**（来自 A1–A5），后手执叉（来自 A6–A9）
- 即：若机器人先 → 机器人用圆料、用户用叉料；若用户先 → 用户用圆料、机器人用叉料
  （★ 若你其实想"用户永远执圆"，说一声，改成按人固定）

### 2.4 难度三档（用户口径：入门 / 普通 / 困难）

| 难度 | 算法 | 行为 | 保底 |
|---|---|---|---|
| **入门** | 随机为主 | 80% 随机、20% 拦截 | 会输 |
| **普通** | 启发式 | 能赢就赢 > 堵你三连 > 占中点/角 > 随机 | 偶尔失误 |
| **困难** | **Minimax 全搜** | 攻守最优 | **永不输**（最好结果是逼平） |

> 井字棋状态空间极小（≤9! = 362880），Minimax 可**离线即时**算完，无需大模型、无需联网 ——
> 这符合本项目"AI 只做受限决策"的口径，且开局可命中固定最优着法。

### 2.5 胜负判定

- 横三 / 竖三 / 斜三 → 胜
- 9 格填满且无三连 → **平局**
- 结束时：屏幕明确显示「你赢了 / 你输了 / 平局」+ 获胜三连线高亮
- **用户赢** → 特效（高亮动画）+ 语音播报「恭喜你赢了，真棒，是个好榜样！」类祝贺语（用户口径 3）

## 3. 交互设计

### 3.1 双输入（用户口径：键盘 + 鼠标都可以）

| 输入 | 行为 |
|---|---|
| **↑ ↓ ← →** | 移动 2D 棋盘上的**光标高亮格**（碰到边界夹住，不环绕） |
| **Enter** | 在光标格**落子**（空格才可下；已有子 → 提示"这格有子"） |
| **鼠标点击** | 直接在该格落子 |
| **鼠标悬停** | 与该格同步移动光标（可选，见 §11-③） |

- 落子输入**仅在「轮到用户」且机器人空闲**时接受；机器人执行/思考期间**禁用**（用户口径：只能停止）

### 3.2 右侧「井字棋」卡片（用户口径：右侧新增功能）

位置：**分拣页右侧栏**（与 A/B 点位设置同页 —— 因为棋盘就是 B 区、点位与搬运链路同源）

```
┌ 井字棋 ────────────────────────────┐
│ 难度  [入门] [普通] [困难]          │  ← 三档单选，开局后锁定
│ 先手  随机（本次：机器人先）        │  ← 开局后显示结果
│ 轮到  你（○）／ 机器人（✕）         │
│ ───────────────────────────────── │
│ [开始] [暂停] [停止] [复盘]        │  ← 暂停⇄继续 同钮；停止=作废
│ ───────────────────────────────── │
│ 进度  第 3 手 · 机器人搬运中…       │  ← 当前动作/阶段
│ 结果  进行中 / 你赢了 / 平局        │
└───────────────────────────────────┘
```

### 3.3 2D 棋盘浮层（叠加在 3D 视口上）

- 位置：分拣页**左侧 3D 视口**内，浮层（复用 `MonitorLayout` 的 `#hud` 插槽，与 SafetyChip/字幕同层）
- 内容：3×3 网格、双方棋子（○ / ✕）、光标高亮框、轮到谁、胜负三连线
- 与 3D 联动：同一格在 3D 里落的料与 2D 格子**一一对应**（同一份状态驱动，见 §6）

## 4. 状态机

```
         ┌──────────┐  开始
         │  idle    │──────────────┐
         └──────────┘              ▼
                              ┌──────────┐
     停止(作废) ┌─────────────│ starting │ 回起点 + 决定先手
                │             └────┬─────┘
                ▼                  ▼
         ┌──────────┐       ┌──────────────┐
         │ stopped  │       │ user_turn    │ ←──────────┐
         │ (作废)    │       │ (等你落子)    │            │
         └──────────┘       └──────┬───────┘            │
                                   │ 用户落子            │
                                   ▼                     │
                            ┌──────────────┐             │
                            │ exec_user    │ 机器人搬圆/叉│
                            └──────┬───────┘             │
                                   ▼                     │
                            ┌──────────────┐             │
                            │ ai_think     │ 三档算法     │
                            └──────┬───────┘             │
                                   ▼                     │
                            ┌──────────────┐             │
                            │ exec_robot   │ 机器人搬运   │
                            └──────┬───────┘             │
                                   ▼                     │
                            ┌──────────────┐   未终局     │
                            │ check_end    │─────────────┘
                            └──────┬───────┘
                                   │ 终局（胜/负/平）
                                   ▼
                            ┌──────────────┐  点击复盘
                            │ finished     │──────────┐
                            └──────┬───────┘          ▼
                                   │              ┌────────┐
                                   └─回起点────────│ replay │ 逐手回放
                                                  └────────┘
```

- **暂停**：在 `exec_user` / `exec_robot` 的**步边界**冻结（复用 `ctx.wait_pause()`），可继续
- **停止**：置取消 → 步边界停 → **棋局作废**（回到 idle，棋盘清空）→ 机器人回起点（用户口径 6）
- **复盘**：终局后可点，逐手回放（默认只回放 2D，见 §9）

### 5.1 新模块 `backend/app/services/tictactoe.py`（纯逻辑，可单测）

> ★ 这一层**不碰硬件、不进线程**，全部可被 pytest 直接钉住（三档算法、胜负、映射）。

### 5.2 新路由 `backend/app/api/tictactoe.py`

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/tictactoe/start` | `{difficulty, dry_run}` → 单例闸 + 点位体检(A/B) + 建 RunContext + 决定先手 + 启动线程 |
| GET | `/api/tictactoe/state` | 棋盘 / 光标无关 / 轮到谁 / 难度 / 阶段 / 进度 / 暂停态 / 胜负 |
| POST | `/api/tictactoe/move` | `{cell}` → 登记用户落子并触发「用户执行 → AI 思考 → AI 执行」 |
| POST | `/api/tictactoe/pause` | 复用 `/control/run-pause` 语义（也可直接前端调 control 端点，见 §5.4） |
| POST | `/api/tictactoe/stop` | 作废 + 回起点（复用 `request_cancel`） |
| POST | `/api/tictactoe/replay` | 逐手回放（返回棋谱序列；前端按序播放） |
| POST | `/api/tictactoe/reset` | 把 B 区已落子搬回 A 区（物料复位，见 §8） |

- 全部 `Depends(require_control)` —— **不做权限后门**（与其它页同一套令牌）

### 5.3 执行线程（复用分拣原语）

```python
# 伪代码（示意，不实现）
def _run_ttt(ctx, difficulty, dry, pmap):
    _move(ctx, pmap, START_POINT, ...)                 # 回起点
    # —— 用户手：已由 /move 登记的 cell ——
    _exec_move(ctx, user_sym, user_cell)               # A正上→A料位→吸→抬起→B正上→停吸→放气→B槽位?
    # —— AI 手 ——
    cell = TT.ai_move(board, ai_sym, difficulty)
    _exec_move(ctx, ai_sym, cell)
    ...
```

- `_exec_move` ≈ 分拣搬一件的**精简版**（无判色、无 C 检测）：
  `A{n}上 → A{n} → 吸 → 等吸牢 → 抬起 → **起点** → B{m}上 → 停吸 → 放气 → 等 → 停放 → 回起点`
  - ★ **用户口径（2026-10-10）**：A→B 下棋时**不许「正上方 → 正上方」直接平移**，
    抬起后先回 **开始/结束点（起点）** 再去 B 正上方落子 —— 避免抬着件在 A/B 两个"正上方"
    之间横扫（扫过托盘/两侧工装）。复位（B→A）保持原路，不经起点。
  - 回归钉：`tests/test_tictactoe_api.py::test_carry_sends_play_via_start`
- ★ **两种模式（2026-10-10 用户口径，见《方案-无法识别一律放回原位》§3）**：
  - **默认**（`verify_color=false`，缺省）：不判色、不去 C 位 —— 就是上面那条行程（节拍快）。
  - **拍照自证**（`verify_color=true`，真实下发时）：抬起后**先送检 C 检测位**拍 3 帧判色，
    颜色必须 = 该格应有的颜色（约定 **圆=红 / 叉=蓝**）；**判不出 / 不符 → 原路放回 A{n} + 停止**
    （统一口径；两种文案分开：一个说"判不出"、一个说"不符"）。
  - 回归钉：`test_carry_verify_unrecognized_puts_back_then_stops` /
    `test_carry_verify_mismatch_puts_back_then_stops` / `test_carry_verify_ok_places_normally` /
    `test_carry_default_mode_never_judges` / `test_verify_mode_needs_camera_point`
- **全程**：`ctx.wait_pause()` 在每次 `_move` 前、`ctx.sleep()` 用于吸牢/放气等待 → 天然支持暂停/继续
- 收尾：无论胜负/停止/异常，`_move(START_POINT)` 回起点（用户口径 4）

### 5.4 暂停/继续 —— 直接复用现有基础设施

后端 `control.py` 的 `RunContext` + `/control/run-pause|run-resume|run-state` **已完整支持**（本会话上一需求刚给分拣接好），
井字棋走**同一套**：

- 暂停 = 原地冻结（步边界生效），可继续
- 停止 = 取消 + 作废 + 回起点
- 前端复用已加的**琥珀色暂停按钮**样式与 `togglePause()` 逻辑（`SortingView.vue`）

## 7. 安全口径（沿用现有铁律，不放松）

| 项 | 口径 |
|---|---|
| 速度 | **沿用右上角那份全局速度**（`exec.speed` → `/start` 的 `speed_pct`，5~100，默认 5）。用户口径（2026-10-10）：**右上角多少，机器人多少** —— 井字棋不再自己写死速度 |
| 围栏 | 每次 `_move` 前 `guard_check()`，互锁不过 → 拒绝并如实报因 |
| 单例 | 分拣 / 执行 / 井字棋 **抢同一个 40135 触发位** → 同一时刻只能一路（后端单例闸拒绝第二个） |
| 空跑 | `dry_run=true`：只走 2D+3D 演示，**不下发、不动机器人**（默认，便于排练） |
| 权限 | 全接口 `require_control`，令牌收回即停 |
| 急停 | 与全局一致：急停 → 停 + 回起点，**对局作废** |
| 互斥 | 对局期间：存点/到点/点动/分拣/Q其他指令全部拒绝（用户口径：只能停止） |

## 8. 物料复位（必须先解决，否则第二局无料可用）

**问题**：井字棋一局最多用满 9 件（A 区全部）。第一局跑完，A 区空、B 区有棋子 → 第二局开不了。

**方案**：`/api/tictactoe/reset` ＝ 机器人把 B 区已落子**搬回**对应 A 格（圆回 A1–A5、叉回 A6–A9），
等价于"逆向搬运"，仍走同一套 `_move`/`_air`。

- 触发时机（三选一，见 §11-①）：
  - **A**（推荐）：终局/作废后，界面提示"点击「复位」把棋子搬回 A 区" —— 人点才动，安全可控
  - **B**：终局自动复位（省事，但真机多跑 5~9 次搬运，耗时长）
  - **C**：不做复位，人工补料（最省机器，但每次要手动摆料）

## 9. 复盘设计（用户口径 7：点击复盘时才进行）

- **触发**：仅终局后可点；点击才播放，不点不动
- **形态**：按 `state.moves` 棋谱**逐手回放**
  - 2D：每手高亮落点 + 序号气泡，可「上一步 / 下一步 / 自动播放」
  - 3D/机器人：**默认不动**（安全）—— 如需"机器人重演整局"，见 §11-③（会真机重复搬运，耗时且有风险）
- **不落库**：棋谱只存内存（刷新即清，与 AI 对话页同口径）

## 13. 手柄输入（Xbox，2026-10-10 追加）

> 用户口径：「我想通过 xbox 玩这个游戏，左右上下、放旗子、开始/暂停、停止等按钮都要」。
> 用浏览器 **Gamepad API** 接入，无需驱动/插件；与键盘、鼠标**同一套逻辑动作**。

**标准映射（W3C "standard"，Xbox 手柄在 Chrome/Edge 下即此布局）**

| 手柄 | 逻辑动作 | 行为 |
|---|---|---|
| **左摇杆** / 十字键 ↑↓←→ | `up/down/left/right` | 移动 2D 光标（左摇杆死区 0.4；首按后 280ms 起每 140ms 连发） |
| **右摇杆 ↑** | `confirm` | **下棋（落子）** |
| **右摇杆 →** | `pause` | **暂停 ⇄ 继续** |
| **右摇杆 ↓** | `stop` | **停止（作废）** |
| **右摇杆 ←** | `replay` | **复盘 ⇄ 退出** |
| **A** | `confirm` | 落子（同右摇杆↑，双保险） |
| **Start / Menu** | `start` | 开始本局 |
| **X** | `pause` | 暂停 ⇄ 继续 |
| **B** | `stop` | 停止（作废本局） |
| **Y** | `replay` | 复盘 ⇄ 退出复盘 |
| **View / Back** | `reset` | 复位（**双击**：第一次提示，3 秒内再按才执行） |

> **右摇杆**（2026-10-10 用户口径："左侧摇杆控制上下左右，右侧是下棋、暂停/继续、停止、复盘等等"）：
> 按列出的顺序**从上方起顺时针**分配。两条硬口径：
> ① **边沿触发** —— 推一次只发一次，必须**回中**后才能再触发（推住不放不会连下好几手）；
> ② **死区 0.7（比左摇杆大）** —— 它触发的是"下棋/停止"，宁可不灵，不可误触中断对局。

**设计要点**

- 纯逻辑抽在 `src/games/gamepad.js`（按键边沿 / 摇杆死区 / 方向连发），**可 headless 断言**（`tools/verify_tictactoe.mjs` 的 K 组）
- 组件**分工不重叠**：棋盘接「方向 + A 落子」，卡片接「开始/暂停/停止/复盘/复位」—— 一次按键不会触发两处
- **只在分拣页响应**（`robot.activeView === "sort"`），不劫持全局手柄
- 手柄**点不了** `window.confirm` → 复位的确认改为**双击 View**（等效确认动作）
- 卡片内显示连接状态（灰=未检测到，青=已连接）；浏览器需先按一次任意键才会唤醒上报手柄

**回归**：`tools/verify_tictactoe.mjs` K 组（按键边沿/死区/方向/映射/接线/不重叠/二次确认）

### 13.1 手柄测试盒（现场自检）

> 用户口径：「手柄能不能控制怎么测试呀？添加一个手柄测试的盒子，点击按钮测试触发什么条件」。
> 位置：分拣页右侧栏（`GamepadTestCard.vue`，可折叠，**状态行常显**）。

| 区块 | 内容 |
|---|---|
| **连接状态** | **有手柄 → 显示「手柄已连接」**（青色）；未连接给"接上后按任意键唤醒"的提示；连上后显示型号 |
| 实时读数 | 当前按下的键（A/↑/Menu…）+ 左摇杆 X/Y —— 现场对号入座 |
| **模拟触发** | 10 个按钮（方向×4 / A 落子 / Start / X 暂停 / B 停止 / Y 复盘 / View 复位）：**点按钮 = 按手柄** |
| 最近动作 | 真按键与模拟按钮都记进同一份日志（时间 · action · 中文），验证"到底触发了什么" |
| 按键 → 动作对照 | 现场使用说明 |

- ★ 模拟走 `gamepad.js` 的 `simulateAction()` —— 与真手柄**共用同一个 `emit()` 广播出口**，
  不是另抄一套逻辑，所以"点按钮测出来的"就是"真按键的结果"
- 井字棋卡片本身也常驻显示「手柄已连接 / 未检测到」，两处一致
- **回归**：`tools/verify_tictactoe.mjs` L 组（`simulateAction` 广播/退订、`readPad` 无手柄安全、文案与接线）

### 13.2 后端来源（Windows XInput 直读兜底，2026-10-10 追加）

> 现场实况：Windows 已认到手柄（`joy.cpl` 确定 / `XnaComposite` OK / `VID_045E&PID_028E`），
> 但 **Edge/Chrome 的 `navigator.getGamepads()` 始终返回 0 个**。
> 用户口径：「直接写后端吧」。

| 层 | 做法 |
|---|---|
| 后端读取 | `services/gamepad.py`：ctypes 调 **XInput**（`xinput1_4 → 1_3 → 9_1_0` 回退）；`XINPUT` 按钮位 → **标准布局下标**（A=0 / Menu=9 / ↑12 ↓13 ←14 →15，与前端 `BTN` 一致） |
| 不漏按 | 后台 **120Hz 采样线程**；`current`=此刻按住，`tapped`=**自上次读取以来出现过**（读一次清一次）→ 前端拿 `current ∪ tapped`，短按（~100ms）也必有一次边沿 |
| 接口 | `GET /api/gamepad/state`（**只读免令牌**，与 `/control/preview` 同类） |
| 前端接入 | `gamepad.js` 新增 `enableBackendFallback(url)`：**浏览器能认就用浏览器**，没有才轮询后端（40ms），把读数包成"假手柄"喂进**同一个 `processPad()`** —— 逻辑动作只有一套 |
| 界面 | 测试盒新增「**来源**」行：浏览器 / 后端（XInput 直读）/ 无；诊断文本含"后端可读(XInput)" |
| 回归 | `tests/test_gamepad.py`（映射、短按不漏、结构、免令牌只读）+ `verify_tictactoe.mjs` M 组 |

- 实测（本机）：`read_raw()` → `connected: True, index: 0, name: "XInput #0"` —— **浏览器读不到、后端能读到**
- 若后端也读不到（非 Windows / 无 XInput）：`available=false`，界面**如实显示**，不假装
